# Languages

Hollin speaks English and Arabic. English is the source language; Arabic is a complete second catalog and the app's first right-to-left language. This file is how a string, a layout and a language are added without breaking the other one.

## How the language is chosen

- Settings > Appearance > Language stores `appearance.language`: `system` (the default), `en` or `ar`.
- `system` is resolved in the main process from the operating system's locale (`resolveLanguage`): a language the app speaks, English otherwise. The smoke test pins the system locale to English.
- Main announces the resolved language with the `language.changed` event and answers `app.language`; the renderer's `I18n` service follows it and sets `<html lang dir>`. Switching applies at once, without a restart.
- What stays in the old language after a live switch, by design: toasts already on screen, a menu or a dialog already open, the plan's snap label until the pointer moves, and the project thumbnails already drawn (each is redrawn the next time it is made).

## The catalogs

`packages/core/src/i18n/`:

- `en/<area>.ts` and `ar/<area>.ts`, one pair per area (`common`, `shell`, `settings`, `library`, `plan`, `tools`, `building`, `decor`, `builtin`, `rules`, `exchange`, `updates`, `assistant`, `errors`, `labels`, `defaults`), merged in `en/index.ts` and `ar/index.ts`.
- A key is `<area>.<what>` in camel case segments: `settings.language.label`. A string used in one place lives in its area; `common` is only for words several areas share.
- A message is a text with `{name}` placeholders, or its plural forms picked by `count`: `{ one: '{count} wall', other: '{count} walls' }`. Arabic gives all six forms (`zero`, `one`, `two`, `few`, `many`, `other`).
- Each Arabic area file `satisfies Record<keyof typeof source, Message>`, so a missing or extra key is a type error there. `i18n.test.ts` checks keys, plural forms and placeholders.
- Command titles are English in the command's definition (agents read that, with the description) and Arabic by command id in `ar/commands.ts`; `commandTitle(meta)` picks. A test fails when a command the palette shows has no Arabic title.
- The English text of an existing string never changes when it moves into the catalog: the smoke test reads it.

## Using a string

- **Renderer:** `protected readonly t = inject(I18n).t;` then `{{ t('area.key') }}`, `[attr.aria-label]="t('…')"`, `[placeholder]="t('…', { name })"`. `t` reads a signal, so templates and `computed`s follow a language switch.
- Never keep a translated string in a field initialiser or a module constant (`readonly tools = [{ label: t('…') }]` is stale after a switch): keep the key and translate where it is rendered.
- **Main and the viewport:** `t('area.key')` from `@studio/core` reads the process language (main sets it from the config; `I18n` keeps the renderer's in step).
- **Errors:** a `StudioError` the user can meet is thrown with a `Phrase` (`new StudioError('CONFLICT', { key: 'errors.level.last' })`): its English `message` comes from `en/errors.ts` and the phrase rides along as `i18n` across IPC; toasts and panels show the translated text (`Toasts.error`, `I18n.error`, core's `errorText`), agents read the English one (`agentPayload` drops `i18n` for MCP and the assistant's model). An error without it shows its English message, isolated left to right, under a translated lead for its code (`errors.code.<CODE>`). The updater's states and the MCP server's status carry a `Phrase` beside their English `message` the same way.
- **Rule warnings** and a connector's broken limits carry a `Phrase` (`text`: `{ key, params }`, a parameter being plain text, a number, a length `{ mm }`, a range `{ mmRange }` or another phrase) next to their English `message`, which is made from it (`ENGLISH_PHRASE`); the Warnings panel and Properties show `I18n.phrase(text, units.length)`, so a warning follows the language and the display units.
- **Built-ins** (furniture, materials, door and window styles) are named by their stable id in the `builtin` area (`builtin.<id>`); the English there repeats the recipe's name, which agents read. Show one through `catalogName(ref, name)` (`I18n.catalogName` in a template): a built-in's name in the language, anything else as it is. Catalog search matches the names in every language. An item's model is shown through `modelName(ref, model)` (`I18n.modelName`), which also translates the stand-in for a lost model (`Missing model` in core, what `plan.describe` and the glTF export say).
- **History labels and default names** (levels, layers, rooms, copies, snapshots, a lamp's light, new projects) are written in the language of the moment and stay as written, for every caller: they are the document's content, in the user's language, so an agent reads `الطابق الأرضي` and `إضافة جدار` in a project made in Arabic, and Otto is told to name what it draws in the user's language. This is the one place agents read the user's language; everything else they read (command results, warnings, errors, `library.info`'s warning, `plan.describe`) is English, with a `Phrase` beside it where a person reads it translated.
- Dates and relative times go through `Intl` with `intlLocale(language)`: undefined in English (the operating system's own format, as before Arabic), `ar-u-nu-latn` in Arabic.

## What stays as it is

- The names: Hollin, Otto, Claude, Claude Code, MCP.
- Command ids, tool names, file names and paths, model ids, JSON, key names (`Ctrl`, `Shift`, `Enter`, `Esc`).
- Unit symbols (`mm`, `cm`, `m`, `m²`, `ft`, `in`) and digits: numbers are shown with Western digits in both languages.
- Everything written for agents: command descriptions, input schemas, the design guidelines, `plan.describe`. The assistant's English prompts are byte for byte what they were, with one exception: the live context (after the cached prefix) always ends with the language sentences (`languagePrompt`), in English too, since a switch from Arabic back to English has to be told; the Claude Code `<app-context>` preamble says "the project or the user's settings changed".

## Right to left

- **Logical classes only.** `ms-* me-* ps-* pe-* start-* end-* border-s border-e rounded-s rounded-e text-start text-end`, never `ml mr pl pr left right border-l border-r rounded-l rounded-r text-left text-right`. `i18n-templates.test.ts` refuses the physical ones outside its short list of exceptions: the space kept for the window buttons in the title bar (the OS never moves them), overlays placed at canvas or pointer pixels, and centring (`left-1/2 -translate-x-1/2`).
- **The canvases never mirror.** A plan is a drawing of a place: x grows to the right in every language. Only the chrome around it flips.
- **Icons that point** (chevrons, arrows, undo and redo, send, the back and forward kind) take `rtl:-scale-x-100`. Icons that do not (check, plus, search, trash, the tools, the marks) stay.
- **Left-to-right islands.** A measurement (`3600 mm`), a coordinate, a path, an id, a model name, a version, a shortcut, a URL or code inside Arabic text takes the `bidi-ltr` class (`direction: ltr; unicode-bidi: isolate`): without it `3600 mm` shows as `mm 3600`. Inputs that hold such text set `dir="ltr"`.
- **Plain-text messages** (toasts, dialog titles, `title` and `aria-label` values, native `<option>`s) have no element for a class: there the Arabic message itself wraps the placeholder in Unicode isolates, written as escapes in `ar/<area>.ts`: U+2066 … U+2069 (left to right) around a measurement, a path, a version, a shortcut or a key name (`Enter`, `Shift+S`, `Home`), an angle with its `°` or a percentage, U+2068 … U+2069 (first strong) around a name people wrote. English messages stay without them (the smoke reads them byte for byte), and `foldForSearch` drops them, so a search still matches. A composed option is a message too (`plan.levelOption`: `{name} · {elevation}`), never two interpolations side by side. `i18n.test.ts` fails on an Arabic message whose measurement-like placeholder (`{length}`, `{elevation}`, `{version}`, `{path}`, `{shortcut}` …) is not isolated.
- **Measurements inside Arabic text are islands even with the right `dir`:** after an Arabic letter, bidi rule W2 reads European digits as Arabic numbers and the unit lands before them (`mm 3000`). A template gives the measurement its own `bidi-ltr` element; a composed string isolates it; free text with lengths in it (Otto's replies) goes through `ltrIslands`. A field holding a length is `dir="ltr"` (`xLength` is; a dialog's `FormDialogField` with `mono` is).
- **Quotes:** Arabic messages quote a name with « » (`«\u2068{name}\u2069»`), not straight quotes.
- **Text people wrote** (project, level, layer and room names, descriptions, labels, tags, chat messages) may be in either script whatever the interface is: its element and its input take `dir="auto"` (in an SVG, which has no `dir`, the text element carries `data-user-text`). Text that can hold several paragraphs in different scripts (Otto's replies) is split into lines, each with `dir="auto"` (core's `chatBlocks`; a blank line is an empty line of its own, so the reply looks and copies as written), and its measurements are islands (`ltrIslands`): `3600 mm` after an Arabic word would otherwise read `mm 3600`. Digit groups with plain spaces between them are one number only before a unit (`3 000 mm`); `101 102 103` stays three numbers.
- **Canvas text** has no `dir`: set `ctx.direction` for every text from `textDirection(text)`, and `ltr` for numbers; a right-to-left text has its measurements isolated before it is drawn (`isolateMeasurements` from core: a label `المدخل · 3600 mm`, a snap name with its length, Otto's tag). Words beside a symbol are placed by core's shared geometry so the canvas and the exports agree (`walkLabelPlacement`: an Arabic UP/DN or riser count starts at a gap beside a stair's start dot and reads away from it).
- **Pointer maths.** Anything computed from `clientX`, `scrollLeft` or a rect's `left`/`right` (drag to reorder, splitters, the tab strip's wheel) must work in both directions.
- Letter-spacing breaks Arabic joining and Arabic has no italics: `styles.css` resets both for every element whose language is Arabic (`:lang(ar)`). A Latin-only mark (the wordmark, the product name on Home and in About) carries `lang="en"` and keeps its tracking. Do not add `tracking-*` to text that can be Arabic without checking it in Arabic.
- **No Arabic words in the mono face.** `--font-mono` falls back to IBM Plex Sans Arabic for the letters, but its own wide space spreads Arabic words apart (`طابق   واحد`). An element that mixes a translated word with numbers keeps `font-mono` for English and takes `rtl:font-sans` (a Home card's level count, About's version line, a connector's derived lines, the footer, the textarea control); numbers and codes inside keep `font-mono` on their own element.
- A **palette form** is a command's schema, written for agents in English: in Arabic its title is translated, each field is named by its key, as code, and the English descriptions are left out.

## Typing

- An Arabic keyboard may type Arabic-Indic digits (٠ to ٩) and the Arabic decimal separator: every parser of a number, a length, an angle or a coordinate passes its text through `toLatinDigits` first (`parseNumber` for a plain number). `parseLength` also reads the Arabic metric symbols (`مم`, `ملم`, `سم`, `م`), `parseAngle` reads `درجة`, and `parseCoordinate` takes `،` and `؛` between x and y.
- **No `type="number"` fields:** Chromium drops Arabic-Indic digits from them before the page sees the value. A number field is `type="text"` with `inputmode="decimal"` (`numeric` for a whole number such as the MCP port), `dir="ltr"`, a string in its form model, and `parseNumber` with the same validation messages a number field had (the export dialog's pixel sizes, the DXF import's scale and origin, the MCP port).
- Shortcuts are the Latin letters on the keys. On an Arabic layout `event.key` is an Arabic letter (Ctrl+K writes ن, Ctrl+, writes و), so every shortcut reads the key through core's `latinKey` (`i18n/keys.ts`): the physical key (`event.code`) when `key` is not a Latin letter or Latin punctuation. Shift on a letter key that writes ASCII punctuation there is the capital (Arabic 101: Shift+L writes `/`, Shift+Z `~`). A Latin letter with a diacritic (ń, ł, ő) is taken as typed, and nothing is remapped while Ctrl and Alt are both held (AltGr on Windows types a character, not a shortcut). The plan's editor, the shell's shortcuts (`ShellActions.handleShortcut`), the palette's Ctrl+N/J/P/K and the 3D view's walking keys all do; a new shortcut must too.
- Enter in a field that sends or submits is ignored while an input method composes (`composing(event)` from `@studio/ui`: `isComposing` or key code 229): Otto's composer, the empty level's Otto line, first launch's.
- Searches (the palette, projects, the catalog) compare `foldForSearch` forms, which drop Arabic diacritics and unify the letter forms people interchange (أ/ا, ى/ي, ة/ه).

## Fonts

IBM Plex Sans Arabic (text, 400/500/700) and Markazi Text (headings, variable, `size-adjust: 116%`), both OFL 1.1, sit after Alegreya Sans, IBM Plex Mono and Fraunces in the font stacks with an Arabic `unicode-range`, so Latin text keeps its faces and Arabic text gets its own. The plan draws its first frame at once and again when the faces have loaded (`loadPlanFonts`, with an Arabic sample); a thumbnail or a snapshot waits for them, at most 3 s, so a face that never loads delays nothing for ever.

Exports: a PDF embeds IBM Plex Sans Arabic Regular (a TrueType file in `resources/fonts/`, shaped and ordered by core's `exchange/arabic-shape.ts`), an SVG names it in its font stacks, a DXF writes Arabic in logical order; CAD layer names stay English (`packages/modules/exchange/README.md`).

Why these two: Plex Sans Arabic keeps a pen's modulation, so it sits beside Alegreya Sans, reads at 11 px, and is the sibling of the Plex Mono the numbers are set in. Markazi Text is a soft, warm naskh with the bookish weight Fraunces gives the Latin headings; it is drawn small on its body, so its `@font-face` carries `size-adjust: 116%`. Both were chosen against Noto Naskh Arabic, Amiri, El Messiri, Noto Sans Arabic, Almarai and Readex Pro in the app's own colours.

## Checking it

- `npm test`: `i18n.test.ts` (same keys in both catalogs, plural forms, placeholders, isolated measurements, the most shown plurals at 0, 1, 2, 3, 11 and 100), `keys.test.ts` (`latinKey`), the guard tests `packages/modules/i18n-templates.test.ts` (no words in a template, no physical direction class) and `packages/modules/commands-i18n.test.ts` (every shown command has an Arabic title). Their pending lists are empty and stay so.
- `npm run smoke`: the Arabic section (`src/main/smoke/arabic-ui.ts` and the files it calls) switches to Arabic through Settings and walks every tab, panel, dialog, menu and state (`arabic-walk.ts`), and checks each screen with `auditArabic` (`arabic-audit.ts`): visible text, `title`, `aria-label`, `placeholder`, `alt` (also of controls revealed on hover) and native options must hold no Latin words outside `LATIN_ALLOWED` (the names, unit symbols, formats, the credits; `Claude Desktop` and `Markazi Text` only whole; the paper sizes Letter, Legal and Tabloid only in the export dialog's sheet select; key names only in a `kbd`, an island or between isolates) and no `undefined`, and a word people wrote excuses only the element that holds it; the section view's SVG text is audited, except what people wrote there (`data-user-text`); a measurement or a shortcut in right-to-left text must be drawn number before unit; a field holding a length must read left to right; a plain string with Arabic and a measurement must isolate it. User text is not checked: it is in a `dir="auto"`, `dir="ltr"`, `.bidi-ltr`, `code`, `kbd` or `bdi` element, where this file puts it. Screenshots 77 to 170, light and dark.

## Adding a language

1. Add it to `LANGUAGES` in `packages/core/src/i18n/index.ts` (its id, its own name, its direction) and to `appearance.language` in the config schema; `resolveLanguage` then matches a system locale to it, and Settings lists it under its own name.
2. Copy `ar/` to `<id>/`, translate every area file (each `satisfies Record<keyof typeof source, Message>`, so a missing key is a type error) with the plural forms its CLDR rules use (`Intl.PluralRules`), merge them in `<id>/index.ts`, add command titles in `<id>/commands.ts`, and register the catalog in `CATALOGS`. `i18n.test.ts` checks keys, forms and placeholders against English.
3. A script outside the bundled faces' ranges needs a face: add its `@font-face` with a `unicode-range` after the Latin faces in `--font-sans`, `--font-mono` and `--font-display` (`src/renderer/src/styles.css`), its sample to `loadPlanFonts`, and, for the PDF, a TrueType file in `resources/fonts/` and the writer's script handling (`exchange/arabic-shape.ts` is Arabic's).
4. A right-to-left language gets everything above for free; another left-to-right one needs nothing more. Run the smoke's Arabic section as the model for a section of its own.

Write Arabic the way good Arabic software does: Modern Standard Arabic, no word-for-word calques, no diacritics except where a word is ambiguous without one (none on the final ة of a counted noun: `11 غرفة`). Sentences end with the Arabic full stop's usual `.`, lists use `،`, and a question uses `؟`.

- **Buttons** are verbal nouns (حفظ، تصدير، إعادة التحقق); Otto's own lines stay conversational, and its confirm pair reads اسمح / أبقِه.
- **Toasts** that report something done read تم… (تم حفظ النسخة، تم نقل «…» إلى سلة المحذوفات); **status lines** take the passive (حُفظ الآن، عُدّل قبل دقيقة).
- **"Already"** is مسبقًا, or the word is dropped; never بالفعل.
- **No clitic on a Latin word or an isolate:** و، لـ، بـ never attach to `Claude`, `Shift` or a placeholder between isolates (`وClaude Code`, `لـ Claude Code`, `بـ«{name}»` read badly and break the isolate). Rephrase so the clitic lands on an Arabic word: «مثل Claude Desktop أو Claude Code»، «الطلاء بمادة «{name}»»، «واضغط Shift».
