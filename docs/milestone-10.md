# Milestone 10: release

The brief's milestones end at 9, but it names two things for "later": electron-updater for in-app updates, and an updater under `src/main`. This milestone makes the app releasable: the exports checked by independent readers, a version and a changelog, in-app updates, signing and notarization ready to switch on, and a release workflow that builds the installers and publishes them to GitHub Releases from a tag.

The repository stays local until the owner asks for GitHub (`CLAUDE.md`). Everything here is prepared and verified locally; the owner's own last step, outside this milestone, is to create the GitHub repository, push `main`, add the secrets and push the first tag. Nothing in this milestone creates a repository, pushes, or depends on one existing.

Four steps, each verified (`npm run typecheck`, `npm test`, `npm run smoke`, screenshots looked at for UI) and committed on local `main` on its own, then a review of the whole milestone and a fixes commit.

## Design

- **Independent readers first.** Milestone 9's DXF, PDF and GLB writers were only ever read back by the app's own readers and the unit tests. Before anything ships, the files are checked by readers the app did not write: `ezdxf` (its `audit`, entity and layer counts) and `pypdf` (page count, page sizes, text extraction, a strict parse) in a throwaway Python environment outside the repository, and the Khronos `gltf-validator` run through `npx` (no dependency added). Writer bugs they find are fixed in core with a unit test each; what they report is recorded in the exchange README's Verified by section with the tool versions and the date.
- **The updater is a host service with a fake for the smoke**, like the dialogs. `src/main/updater.ts` wraps `electron-updater`'s `autoUpdater` (`autoDownload: false`, `autoInstallOnAppQuit: true`): the host owns an `Updater` interface (`check`, `download`, `install`, `status`) and the smoke passes a scripted one, so the smoke never touches the network and the UI's states are all checked. The state is one record `{ state: 'idle' | 'checking' | 'available' | 'up-to-date' | 'downloading' | 'ready' | 'error' | 'unsupported', version?, notes?, progress?, message?, checkedAt? }`, announced as `update.changed` (`HostEvents`). `unsupported` covers a build with no update feed (a local `npm run package`, a dev run, the smoke, a `.deb`, an unsigned macOS build, which electron-updater cannot install).
- **Update commands are hidden.** `app.update.status`, `app.update.check`, `app.update.download` and `app.update.install` are UI plumbing: an agent must never be able to download or install code. They are hidden like `config.update`.
- **The feed is GitHub Releases, configured by the build, never by hand.** `electron-builder.cjs` sets `publish` only when `GITHUB_REPOSITORY` is in the environment (the release workflow), split into owner and repo; a local `npm run package` has no `publish`, so electron-builder writes no `app-update.yml` and the app reports `unsupported`. Nothing names the owner or repository in the source.
- **Signing is ready, not required.** The configuration signs when the secrets are present and builds unsigned when they are not, so the workflow runs today and keeps running once certificates exist: Windows through `CSC_LINK`/`CSC_KEY_PASSWORD` (electron-builder's own convention); macOS with hardened runtime and entitlements, `identity` left to electron-builder when `CSC_LINK` is set and `null` otherwise, notarization through `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD` and `APPLE_TEAM_ID` when set. `docs/release.md` says which secrets to add and how a release is cut.
- **A release is a tag.** `release.yml` runs on `v*` tags (and by hand, without publishing): one job per platform builds with `electron-builder --publish always` into a draft GitHub Release named after the tag, which the owner reviews and publishes; the version comes from `package.json` and must match the tag, which the workflow checks. The changelog (`CHANGELOG.md`, Keep a Changelog form) is the release's notes.

## Steps

### Step 1: the exports read by independent readers
- A throwaway Python environment in the scratch folder (never in the repository, nothing added to `package.json`): `python -m venv`, `ezdxf`, `pypdf`. `npx --yes gltf-validator` for GLB (check the package exists and runs; if `npx` cannot run it, download the Khronos validator binary into the scratch folder instead).
- A node script in the scratch folder (run with `npx tsx` or built with `vite-node`, whichever the repository already has; else a small vitest file under `packages/core/src/exchange/` marked `.manual.test.ts` and excluded from `npm test` by `vitest.config.ts`) that writes, from the unit tests' fixtures (`house.fixture.ts`, the two-level house of `gltf.test.ts`): a DXF per level, an SVG per level, one PDF with every level at 1:100 on A3 and at `fit`, and a GLB with items and finishes. Also the smoke's duplex: run the smoke's export section with a fixed output folder, or add `SMOKE_KEEP=<dir>` that copies the exchange section's files there.
- Read each: `ezdxf.readfile` + `audit()` with zero errors, the layer names and entity counts per layer match the drawing's, every LWPOLYLINE with a bulge resolves to the arc the drawing had (compare a door swing's radius), TEXT and MTEXT read back; `pypdf.PdfReader(strict=True)` opens the PDF, the page count is the level count, each page's media box is the paper size in points, `extract_text()` holds the level names and the title block, and the xref needs no rebuild (no warnings logged); `gltf-validator` reports zero errors and zero warnings of severity above info, the node names are the level names, and the material count is as expected.
- SVG: open in Chromium headless (the smoke window, or `electron` with a page) and check it renders without console errors, and the viewBox and the `width`/`height` are the paper size.
- Every finding is fixed in the writer with a unit test next to it (`dxf.test.ts`, `pdf.test.ts`, `gltf.test.ts`, `svg.test.ts`); a reader's quirk that is not a bug is written down. The exchange README's Verified by section gains the tool names, versions, the date and what was checked. The milestone-9 deferred items that remain (readers tried a DXF from another program? no: only the app's own output) are listed there too.
- Commit: `Milestone 10, step 1: exports checked with ezdxf, pypdf and gltf-validator`.

### Step 2: in-app updates
- `electron-updater` as a dependency (one-line reason: in-app updates from GitHub Releases, asked for by the brief; it must be a `dependency`, not a dev one, since main requires it at run time; keep it out of `external` only if electron-vite bundles it cleanly, else add it to `external` as the docs for electron-builder advise, and say which in the README). Pin the major.
- `src/main/updater.ts`: `createUpdater(opts)` returning the host's `Updater`: reads `autoUpdater`'s availability (`app.isPackaged`, the feed present: `autoUpdater` throws or logs when `app-update.yml` is missing, so probe for it under `process.resourcesPath` and report `unsupported` with a reason instead of an error), maps electron-updater's events to the state record, `check()` runs `checkForUpdates` with `autoDownload: false`, `download()` runs `downloadUpdate` reporting `download-progress`, `install()` runs `quitAndInstall` after the host stopped (go through the same `before-quit` path so pending writes land). An update found at startup is only announced; nothing downloads without the user. A check on startup 10 s after the window is up when `config.updates.check` is on, never in dev or smoke, at most once per 24 h (`checkedAt` kept in the host's data folder, not config). Release notes (`releaseNotes` from the GitHub release body) kept in the state, plain text only.
- Core: `config.updates.check: boolean` (default `true`), `HostEvents['update.changed']`, the `UpdateState` type, `HostApi.updater`. `src/main/host.ts` takes `updater` in its options (the smoke passes `smokeUpdater` from `src/main/smoke/updater.ts`: scripted by `smoke.updates.script(...)`: a check finds `1.2.3` with notes, a download reports progress 0 → 100 then `ready`, a check that errors, a build that is `unsupported`; `install` records that it was asked and does not quit).
- Commands in a new module `packages/modules/updates` (`main.ts`, `README.md`, registered like the others): `app.update.status` (global, hidden), `app.update.check` (global, hidden), `app.update.download` (global, hidden), `app.update.install` (global, hidden). All hidden; `install` is also `mutating: true` for good measure. `app.about` gains `updates: boolean` (whether a feed exists).
- UI (`packages/modules/updates/ui/` registered in `packages/modules/ui.ts`, shown as a Settings section through the existing `sections()` mechanism, placed as "Updates" before About, or inside About if the mechanism does not allow ordering): the state as one line (`Checking…`, `Version 1.2.3 is available`, `You have the latest version (checked at …)`, `Downloading 42 %`, `Ready to install`, the error message, or `Updates are not available in this build: <reason>`), buttons `Check for updates`, `Download`, `Restart and install`, the notes under it (plain text), and the checkbox `Check for updates when the app starts`. A toast when a check started by the schedule finds a version (`Version 1.2.3 is available`, action `Settings` opening the Settings tab), and one when the download is ready (`Restart and install`). `data-testid`s: `updates-status`, `updates-check`, `updates-download`, `updates-install`, `updates-auto`.
- Smoke (`src/main/smoke/updates.ts` through commands and `updates-ui.ts` in the UI phase): the hidden commands are not in `host.listCommands()` for agents and not MCP tools; the scripted states show in Settings in order, the buttons enable and disable with the state, the toasts appear, `install` reaches the fake, `config.updates.check` follows the checkbox. Screenshots light and dark.
- Commit: `Milestone 10, step 2: in-app updates`.

### Step 3: packaging, signing and the release workflow
- `electron-builder.cjs`: `publish` from `GITHUB_REPOSITORY` only (see Design), `releaseType: 'draft'`; Windows `artifactName` as now and a `portable`? No: NSIS only, keep it; macOS `hardenedRuntime: true`, `gatekeeperAssess: false`, `entitlements` and `entitlementsInherit` pointing at `resources/entitlements.mac.plist` (network client, JIT disabled unless Electron needs `allow-jit`: Electron does, so `com.apple.security.cs.allow-jit` and `allow-unsigned-executable-memory`, `disable-library-validation`), `identity` null unless `CSC_LINK` is set, `notarize: true` only when `APPLE_ID` is set (electron-builder 26's form of the notarize option: read `node_modules/electron-builder`'s typings, not memory); Linux `artifactName` and `maintainer` from `package.json`'s author, `desktop` entry with the category; `generateUpdatesFilesForAllChannels: false`, and the `latest*.yml` the updater needs are produced by the targets the updater supports (NSIS, dmg + zip, AppImage).
- `package.json`: `repository` is not set (the owner adds it with the GitHub repository); `version` stays `0.1.0` for the first release; a `release:check` script that fails when `CHANGELOG.md` has no section for the current version, used by the workflow.
- `CHANGELOG.md` (Keep a Changelog): `0.1.0` with one line per milestone and a line for the fixes pass, and an `Unreleased` section.
- `.github/workflows/release.yml`: on `push: tags: ['v*']` and `workflow_dispatch` (build only, artifacts uploaded, nothing published); a first job checks the tag matches `package.json`'s version and the changelog has the section, runs typecheck and the unit tests; then one job per platform (`windows-latest`, `macos-latest`, `ubuntu-latest`), `npm ci`, `npm run build`, `electron-builder --publish always` (or `never` on dispatch) with `GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}` and the signing secrets passed through from `secrets` (missing ones are empty, which electron-builder treats as unset: confirm, or guard with `if`), `contents: write` permission, the release created as a draft by electron-builder; the smoke is not run here (CI runs it on every push). Timeouts and `concurrency` as in `ci.yml`.
- `docs/release.md`: how a release is cut (bump `version`, write the changelog section, commit, tag `vX.Y.Z`, push the tag, review the draft release, publish it; what the updater then shows), the secrets to add on GitHub for signing and notarization and where each comes from, what works unsigned (Windows SmartScreen warning, macOS Gatekeeper refusal with the right-click workaround, the macOS updater not working unsigned), and how to test an update locally (a `dev-app-update.yml`, electron-updater's own mechanism, pointing at a release of the owner's repository once one exists).
- Verification: `npm run package` locally produces the NSIS installer and `win-unpacked`, no `app-update.yml` in `win-unpacked/resources` (so the app reports `unsupported`), and the packaged app starts: run `release/win-unpacked/<productName>.exe --smoke` once if the smoke harness runs packaged, else start it, wait for its window, read Settings > About through the MCP port is not possible, so take `app.about` through `--smoke`'s harness or just check the process stays up for 10 s and exits on `taskkill /pid` (by pid only). Validate both workflow files with `actionlint` through `npx --yes actionlint` if it runs on Windows, else with a careful read against the actions' current major versions.
- Commit: `Milestone 10, step 3: packaging, signing and the release workflow` (the dependency's reason in the message).
