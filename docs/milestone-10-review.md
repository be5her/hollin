# Milestone 10: review

A review of every change since `72016eb` (the four milestone-10 commits and the plan, read as one diff) for correctness, security (the updater's feed, the hidden commands, the workflow's permissions and secrets), the smoke's coverage and the documentation's accuracy. The library code the findings depend on was read in `node_modules`: electron-updater 6.8.11 (`out/main.js`, which picks the Linux updater) and app-builder-lib 26 (`targets/FpmTarget.js`, which writes `package-type`). Fixed in `Milestone 10: review fixes`.

## Findings

1. **(high) An AppImage may carry the deb's `package-type` and would then update through dpkg.** electron-builder's deb target writes `package-type` into `linux-unpacked/resources` (`FpmTarget.js`, only when the build has a feed), the same folder the AppImage target packs from, in parallel; electron-updater's `autoUpdater` reads that file before it looks at `APPIMAGE` (`main.js`), so an AppImage that caught it gets a `DebUpdater`. **Fixed:** `updateSupport` looks at `APPIMAGE` first and never reads `package-type` then (it now also returns `appImage`), and `src/main/updater.ts` makes `new AppImageUpdater()` itself in an AppImage, `autoUpdater` everywhere else. `release.yml`'s Linux build extracts each AppImage after packaging (`--appimage-extract`, no FUSE needed) and fails when `squashfs-root/resources/package-type` exists, so the race is caught where it happens. Unit test: the support order (an AppImage with a `deb` file is the AppImage, `read` never called; the same files without `APPIMAGE` are the deb). A `CLAUDE.md` gotcha.
2. **(medium) `install()` asked twice could start the installer twice** (the toast's action and the button, or a double click): electron-updater's second `quitAndInstall` resets its `quitAndInstallCalled`, and `autoInstallOnAppQuit` then installs again on quit. **Fixed:** `UpdaterBase.install` keeps the install under way and hands it to a second ask, and `ElectronUpdater.apply` runs once per process. No new state was added (the Settings button already disables itself while its own install runs). Unit test: two concurrent `install()` calls run `apply` once, and an install after the first settled runs again (the smoke's fake stays ready).
3. **(medium) A failed install left the app running with a stopped host:** only electron-updater's `error` event relaunched; a rejected `beforeInstall` or a throwing `quitAndInstall` set the error state and left the app without a host. **Fixed:** `installAfterStop` (in `update-state.ts`) stops the host and hands over to the installer, and sends any failure once the stop has begun to `fail`; `ElectronUpdater.installFailed`, shared with the `error` listener, sets the error and relaunches (`app.relaunch(); app.quit()`). Unit test: a rejected stop and a throwing `quitAndInstall` both reach `fail`, the installer is never called after a failed stop.
4. **(medium) `release.yml` hardening.** The check job had `contents: write` (for the draft) while running `npm ci` and the project's tests; checkouts kept the token in `.git/config`; an existing published release for the tag was uploaded into. **Fixed:** `persist-credentials: false` on every `actions/checkout@v7` (`ci.yml` too); `check` keeps `contents: read` and runs `npm ci`, `release:check`, the typecheck and the tests; a new `draft` job (needs `check`, tag pushes only, `contents: write`, no `npm ci`: `node scripts/release-check.mjs` writes the notes with Node alone) creates the draft and fails when a release for the tag exists and is not a draft (`--jq '.[] | select(.tag_name == env.TAG) | "\(.id) \(.draft)"'`, the tag passed through the environment, never spliced into the filter); the build jobs need `[check, draft]` with `if: ${{ !cancelled() && needs.check.result == 'success' && (github.event_name != 'push' || needs.draft.result == 'success') }}` (by hand `draft` is skipped), keep `contents: write` for the upload, and `GH_TOKEN` stays on the packaging step only. Checked with actionlint (see Verification).
5. **(low) A local Linux `npm run package` failed:** the deb's fpm target refuses to build without a homepage, which came only with `GITHUB_REPOSITORY`. **Fixed:** `electron-builder.cjs` builds the deb only when a homepage is known (`package.json`'s `homepage`, should the owner add one, else the feed's repository): `target: ['AppImage', ...(homepage ? ['deb'] : [])]`. README's `npm run package` row and `docs/release.md` say a local Linux build makes the AppImage only. Unit test: `src/main/packaging.test.ts` loads the config without and with `GITHUB_REPOSITORY` (no feed and AppImage only; the feed, the homepage and the deb; a blank variable counts as none).
6. **(low) The docs said electron-builder treats an empty secret as unset on every platform.** That holds on Windows (an empty `WIN_CSC_LINK` is unset in `windowsSignToolManager`), not on macOS, where an empty `CSC_LINK` counts as a certificate and only the config's `identity: null` mapping keeps the build unsigned. **Changed:** the comments in `release.yml` and `electron-builder.cjs`, `docs/release.md` and the updates README now say so, as `CLAUDE.md` did.
7. **(low) `app.update.download` writes an installer outside the library but was not mutating,** and the smoke check "an MCP caller cannot install, even by name" only proved the mutating gate of `execute`, not what an MCP client can reach. **Fixed:** `download` is `mutating: true`; the smoke check is now "download and install are also mutating", the gate check is named for what it proves and covers download as well, and a new check calls `app_update_install` and `app_update_download` by name with an MCP client: the SDK answers an unknown tool with a protocol error (`Tool … not found`, a rejected `callTool`; an error result would be accepted too), and nothing is downloaded or installed. The README's Agents section says the real protection is that hidden commands are not tools.
8. **(low) Two timing-bound smoke steps.** "A check the user asked for brings no toast" waited 500 ms; and the ready toast's action was clicked after `showSection()` and `smoke.shots()` (two theme switches and two captures), which can outlast the toast's 6 s on CI. **Fixed:** a `MutationObserver` installed before the check records every toast message; after the ready toast has come, the check reads the recorder (the ready toast is there, no "is available" one). The toast's action is clicked as soon as the toast is seen, and the screenshot taken after.
9. **(low) Settings > Updates refetched `app.update.status` over IPC on every `update.changed`** (up to a hundred per download). **Fixed:** the section asks once when it opens and then takes each state from the event's payload (`injectHostEvent`); a seed answered after an event is dropped as stale. Smoke check: no `app.update.status` call reaches the host during a download of eight progress steps.
10. **(nit) A check or download let go after `reset()` or `setUnsupported()` overwrote the newer state.** **Fixed:** `UpdaterBase` has a generation counter bumped by `restart` (used by `setUnsupported` and the smoke's `reset()`); a check or download from an older generation ends without touching the state (nor the stamp file). Unit test with a held updater: a held check let go after a restart leaves `idle`, a held download let go after the build turned unsupported leaves `unsupported`.
11. **(nit) The startup check ran even when the app was stopping, and an app left open never checked again.** **Fixed:** `scheduleChecks` (in `update-state.ts`, used by `index.ts`) checks 10 s after the window has loaded and then asks every hour (`setInterval(...).unref()`), running a check when `startupCheckDue` says the last one is a day old, and never once `stopped` is set. README and `docs/release.md`: "10 s after start and then once a day while it runs". Unit test with fake timers. **Noted, not changed:** on macOS with a feed, `updateSupport` runs `codesign -dv` synchronously at startup (10 s timeout at most); see 14.
12. **(nit) Screenshot names collided:** `58-settings-updates-downloading` and `59-settings-updates-ready` shared their numbers with `58-snapshot-3d-day.png` and `59-snapshot-3d-night.png`, which `decor-agent-ui.ts` writes directly. **Fixed:** the update shots are `61-settings-updates-downloading`, `62-settings-updates-ready` and `63-settings-updates-unsupported` (updates README; a `CLAUDE.md` line on numbering).
13. **(nit) Settings > Assistant's Save key wrapped onto two lines** in its flex row beside the 24 rem key field. **Fixed:** `shrink-0 whitespace-nowrap`, as Check again beside it has. Smoke check: the button's text lies on one line.
14. **Noted, not fixed:**
    - `plainNotes` collapses the indentation of `<pre>` blocks and leaves rare named entities (`&hellip;`, `&mdash;` …) as written. No security impact: the notes are shown through Angular's interpolation, which escapes them, never as HTML; GitHub's release bodies rarely carry either.
    - The macOS `codesign` probe runs synchronously at startup (bounded by its 10 s timeout) when the build has a feed. It runs once, only on macOS release builds; making it asynchronous would mean the updater's support is not known when the host starts. Left for when a macOS release exists to measure.
    - Builds run by hand (`workflow_dispatch`) carry the repository's feed, since `GITHUB_REPOSITORY` is set in every run: an installed one updates like a release would. That is intended (the plan's outcome says so) and they are only kept as artifacts.

## Verification

- `npm run typecheck`: no errors (the 13 Angular template warnings it printed before these fixes, unchanged).
- `npm test`: 72 files, 602 tests passed (the two load-bound tests passed in the full run).
- `npm run smoke` with `SMOKE_SHOTS`: passed, 890 checks in 149 s, no stale Electron process before it.
- actionlint 1.7.12 with shellcheck, on `release.yml` and `ci.yml`: 0 errors (the shellcheck rule enabled; only pyflakes, not installed, disabled).
- Screenshots, light and dark: `61-settings-updates-downloading` shows `Downloading 42 %` with every button disabled and the notes under *What's new in 1.2.3*; `62-settings-updates-ready` shows `Ready to install version 1.2.3. It also installs when you quit.` in green with only Restart and install enabled, no toast left over; `63-settings-updates-unsupported` shows `Updates are not available in this build: this build has no update feed (only release builds have one)` with every button disabled. In all three the Assistant's Save key sits on one line beside the key field. `58-snapshot-3d-day.png` and `59-snapshot-3d-night.png` are no longer overwritten.
- Not run: a real Linux build (no Linux machine here), so the AppImage check in `release.yml` and the AppImage-only local package were checked by reading app-builder-lib and by `packaging.test.ts`, not by building; the real electron-updater install path, as before, needs a published release.
