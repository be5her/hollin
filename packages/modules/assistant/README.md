# Assistant

The in-app assistant, **Otto**: a chat with Claude inside the project tab, with every command of the app as its tools. Two providers, chosen in Settings > Assistant (`config.ai.provider`): the **Claude API** with the user's own key (the default, and the only path supported for anyone but the user), or the user's own installed, logged-in **Claude Code**, driven as a subprocess ("bring your own Claude Code", see Compliance below).

- **The panel** (`ui/assistant-panel.ts`, the **Otto** tab of the project's right column, with the 16 px mark; `design/identity/03-otto.md` §b). The header: the 28 px mark, "Otto" in Fraunces, under it the model in mono (the API model's name, or "Claude Code <version> · <model> · <effort>") and the rule "asks before deleting", and Clear. Your messages sit on the elevated paper, right-aligned; Otto's are plain paragraphs with a 2 px mulberry rule (a caret blinks at the end while one streams). Every tool call is a paper card with a 3 px mulberry left edge: a status glyph (a mulberry spinner while it runs, a moss check when done, a camera for a snapshot, the shield greyed when declined, a filled square when stopped, a danger circle when it failed), the title (a `plan.apply` batch's label, else the command's title), the command id in mono, and a second line with what the call carried: the level and layer of the undo step it left and "undoable, by Otto", or for a batch the level, "N edits" and "one undo step, by Otto", "read only" for a query, the level and the view ("plan", "3D, night") for a snapshot, whose image shows under it (click for its full height). A destructive call is the waiting card: an ochre shield and border with the mulberry edge, "Otto asks before deleting." with the target ids when the input names any, the input in a mono well, and **Allow** (terracotta) and **Keep it** (paper); the card takes focus itself, never Allow. Long summaries and inputs are clipped to three lines with More. "Working…" with the mark shows until something streams; a failed run shows its error in danger and **Send again** (Open Settings for a refused key). Scrolled up while Otto writes, a "New from Otto" pill brings you back down. The empty conversation: the mark, "Tell Otto what the place is.", the rule, and two example sentences that go into the message field. The composer: "Ask Otto…", Enter sends and Shift+Enter is a new line, the hint "Edits land on your undo stack, signed Otto." with the key caps; Send swaps to **Stop** while Otto works (Esc in the panel does the same), and after Stop with Claude Code a spinner and "Stopping the last run…" until the process is gone. Setup states replace the chat (the header's second line says the state): "Otto needs a key, or your Claude Code." with **Set up Otto** (Settings > Assistant), Claude Code not found (Open Settings, Check again), Claude Code not logged in in Otto's voice (Check again). With Claude Code and the MCP server off, a notice with **Enable MCP server** sits above the composer. Home's composer and the empty project's Otto line send their sentence as the chat's first message (`assistant.send`); when that is refused (a run already going), the sentence is handed over instead (`AssistantDrafts`) and lands in the message field, unsent. It loads `assistant.state` when it opens and follows `assistant.event`; snapshot images come from `assistant.image`; replies are plain text.
- **What the cards do not show yet:** the target's size and layer on the waiting card (the confirmation carries the command and its input only, so the card names the ids the input holds); the level of an edit whose input names none and that left no undo step; app notes (a resume failure, the round limit) are ordinary Otto paragraphs, not the italic note style; the provider picker inside the panel (the setup state opens Settings).
- **The status bar** (`ui/otto-presence.ts`): the module's `setup` starts `OttoPresence`, which follows every chat (`assistant.event`), `assistant.status` and `assistant.probe` and publishes the state of the project on screen as `AppState.assistant`: "Otto · ready", "thinking…", "reading the plan…" (a read-only call), "looking at the plan…" / "looking at the 3D view…" (a snapshot), "<the batch label or command title>…" (an edit), "writing…", "waiting for your yes", "stopping…", "stopped" (3 s), "couldn't reach Claude" (6 s, after a failed run), and the setup states "needs a key", "checking Claude Code…", "Claude Code not found", "Claude Code not logged in", "needs the MCP server". The shell draws it (see `src/renderer/README.md`); History reads the pending call from it, and the plan its targets (`pending.ids`, the entity and connector ids the waiting call's input names, from `targetIdsOf` in core), which it outlines dashed until the user answers.

- **Where it runs:** in the main process (`main.ts`). The API key never leaves main, tool calls run as `caller: 'assistant'` with the model id or the Claude Code version as the agent, and the question whether a destructive command may run is asked in the chat. The renderer only sees host events and a few hidden plumbing commands. `main.ts` keeps one chat per open project and picks a provider per run (`ChatProvider`: `send`, `stop`, `dispose`); both providers report through the same `LoopEvents` (`text`, `toolStart`, `toolEnd`, `note`), so the transcript, the cards and the events are the same whichever runs.

## The Claude API provider (`loop.ts`)

- **The loop:** one user message starts a run. Each round streams a reply (`client.messages.stream`); when the model asks for tools, every call runs through the registry and the results go back in one user message, until the model ends its turn, is stopped, or has used 25 rounds of tool calls. Image results (commands declared `output: 'image'`, i.e. `view.snapshot`) go back as image blocks, so the model sees the plan it changed. No `thinking` parameter is sent: the listed models think adaptively by default. `max_tokens` is 16,000.
- **Tools:** every non-hidden command, named as for MCP (`toolNameFor`: `plan.wall.add` is `plan_wall_add`), with its zod input as JSON Schema (`toolInputSchema`) and its description plus a note when it is gated. Hidden commands are never offered, and a tool name the model makes up is answered with an error result. Project tools act on the chat's project.
- **System prompt:** who Otto is and who it works for (homeowners and hobbyists planning their own place), how to work (read first, change in one `plan_apply` batch whose label is a short verb phrase, since it names the History row, the card and the status bar; look at the result), Otto's voice in short (`03-otto.md` §a: the result first, every length with its unit in millimetres, names not ids, say the choice made, one question at a time, say when it looked, ask before deleting and say what goes with it, errors with the way out, "I" and "you", plain text without exclamation marks, past tense for what is done), `DESIGN_GUIDELINES` from core (the same text the MCP resource serves), then the live part: the project's name, its levels with ids and elevations, and the user's display units. The stable part carries a cache breakpoint.
- **Failures:** API errors end the run with a short reason (`error` in the chat state: a refused key, rate limiting, no connection); the API history is trimmed back to before the failed message, so the conversation never ends mid-round. Stopping a run (`assistant.cancel`) while a reply streams aborts the request the same way. Every `tool_use` is answered by a `tool_result`, since the API refuses a conversation with an unanswered call: stopped between the calls of a round, the calls that did not run are answered with an error result ("Not run: the user stopped the assistant.") and the round is kept, so the model knows what ran; at the round limit the last round's calls are answered the same way ("Not run: the limit of 25 rounds …").
- **Pointing the SDK elsewhere:** the environment variable `STUDIO_AI_BASE_URL`, read when a run builds its client, replaces the API's base URL. The smoke test sets it to its fake API (`fake-api.ts`); it also serves a proxy. Never set in normal use. The fake answers a request with a `tool_use` left without its `tool_result` in the next message with the real API's 400 (`unansweredToolUse`).

## The Claude Code provider (`claude-code.ts`)

- **The binary:** `config.ai.claudeCodePath`, or `claude` on PATH (`findClaude`: a PATH and PATHEXT scan, never by image name). The native build is run directly; an npm install's `.cmd` shim is resolved to its `cli.js` and run through the app's own executable as Node (no shell is ever used); a `.js`/`.cjs` path (the fake) runs the same way. `assistant.status` probes it with `claude --version` and `claude auth status --json` (neither consumes usage), caches the answer per path, and probes again on `refresh` (the Check again button) or after a run that failed to authenticate.
- **One process per chat**, started on the first message and kept for the chat's life: `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --replay-user-messages --max-turns 25 --tools "" --mcp-config <the app's server only> --strict-mcp-config --allowedTools mcp__<server>__* --disallowedTools Bash,Edit,Write,Read,WebFetch,WebSearch --append-system-prompt <the same prompt the API provider sends, the live part as it stood at start> [--model <m>] [--effort <e>] [--resume <id>]`, in `<data folder>/claude-code` (an empty folder the app owns, so no project CLAUDE.md is picked up). `--tools ""` removes the whole built-in set, so Claude Code can only act through the app's commands; the user's other MCP servers are never loaded. User turns go in as stream-json user messages; the reply's text deltas, the tool calls (`assistant` messages) and their results (`user` messages) come out as stream-json lines and become `text`, `toolStart` and `toolEnd`; the turn ends with Claude Code's `result`. Stop kills the process (`taskkill /pid <pid> /t /f` on Windows, SIGKILL elsewhere); the next message starts a fresh process that resumes the same session. Closing the project or quitting kills it too, and so does the MCP server stopping or moving (a note says so). The model and effort come from Settings (`config.ai.claudeCodeModel`: an alias such as `opus` or a full id, `config.ai.claudeCodeEffort`: `low` … `max`; empty leaves Claude Code's own default, which is whatever the user's Claude Code is set to); a change applies from the next message, whose process is started again on the same session, and the panel's header names them ("Claude Code 2.1.283 · opus · high effort"). A model name must start with a letter or digit, so it can never read as a flag.
- **Tools over the app's own MCP server.** The server is never started by the assistant: while it is off (`config.mcp.enabled`), `assistant.send` is refused with `UNAVAILABLE` and the chat shows the notice with the "Enable MCP server" button, which runs the same `config.update` Settings uses, as the user's own click. The URL Claude Code gets is `http://127.0.0.1:<port>/mcp?project=<id>&assistant=<token>`: the token is 32 random bytes per process, kept only in this module's map while the process lives, never logged (call-log entries carry the tool, the agent and the project). The MCP server asks `host.identifyAssistant` (installed by this module) and, for a known token, runs the call as `caller: 'assistant'`, `agent: 'claude-code <version>'`, bound to the chat's project, inside the chat's `AsyncLocalStorage` scope, so edits are signed Otto in History and mutating calls go through the chat's Allow / Keep it card, not the Settings > MCP switch. Any other MCP client stays `caller: 'mcp'`, token or not. The token sits in the process's command line, visible to the same user on this machine, which is the audience the loopback server already has.
- **Resume.** The session id from Claude Code's `init` event is stored per project in the project's per-machine view state (`assistant.sessionId` in `.local/ui.json`, through `host.projects.setUiState`, which merges keys: not in the design, not in snapshots or exports) and passed as `--resume <id>` whenever a process is started for that chat again: after Stop, after the project is reopened, after the app restarts. Everything the stream prints before the echo of the turn's own message (`--replay-user-messages`) is the resumed session's history and is rebuilt into the transcript before the new message, unless the transcript was restored from the view state (see Storage), which is the normal case; Claude Code 2.1 itself replays nothing on resume, the fake does. A resume that fails because the session is gone (the session was deleted, Claude Code was reinstalled) forgets the id, says so in the chat as a note and starts a new session with the same message. What the real binary prints for a lost session was not checked by hand, so only a failure before the process's first answer whose error or stderr names the session id counts (the fake prints "No conversation found with session ID: <id>"); any other failure of a resumed process (a crash, a refused connection) ends the run with its reason and keeps the session for the next message. The echo of the turn's own message is told from replayed history by its `isReplay` flag, never by its text, so an earlier message with the same words stays history. Clear kills the process, forgets the id and starts a new session next time.
- **The live context.** The prompt's live part (the project's name, its levels, the display units) goes into `--append-system-prompt` when a process starts. A process is kept for the chat's life, so before each message the provider builds the live part again: when it differs from what the process was last told, the message carries it in front, wrapped in `<app-context>…</app-context>` (the transcript shows the user's own words, and a replayed message loses the wrapper). That is cheaper than starting the process again on the same session: no spawn and no new MCP connection, and the system prompt, the head of Claude Code's prompt cache, stays the same.
- **Failures:** a process that exits mid-turn, a `result` with `is_error`, or an MCP server Claude Code could not connect to end the run with the reason as the chat's error. A logged-out Claude Code answers the first turn with "Failed to authenticate…" (checked against 2.1.283); the status is marked not logged in and the panel shows the matching empty state.
- **Checked against the real binary** (2.1.283, logged in, 2026-10-07, by hand, never by the tests or the smoke): `init` lists the app's server as `connected` and the `mcp__plan-studio__*` tools as the only tools; the wildcard in `--allowedTools` is honoured in `-p` mode, so a tool call runs without a permission prompt; the echo of a stdin turn carries `isReplay: true`; a text block's `assistant` message arrives before the `tool_use` one; a tool result's `content` is an array of text blocks; a second process started with `--resume <id>` continues the session (it answered from the earlier turn) and replays nothing. The environment variable `STUDIO_CLAUDE_CODE_LOG=<file>` makes the provider append every line Claude Code prints (stdout and stderr) to that file, for looking at a conversation that went wrong; never set in normal use.

## Attribution, undo and confirmation (both providers)

- Every edit Otto makes is a transaction with the command's own label and the author `{ kind: 'assistant', name: <model id or claude-code version> }`, so the History panel signs it "Otto · <layer> · <command id>" on Otto's tint and one Ctrl+Z undoes a whole `plan.apply` batch. A tool card reads the undo step its call left (`history().undo[0]`, compared with the one before the call) for its level and layer.
- Mutating commands (deletes, writes outside the library) reach `host.confirmMutation`, which this module installs when it starts. It finds the chat the running tool call belongs to (an `AsyncLocalStorage` around each call, and around each recognised MCP call), puts the request in the chat (`status: 'waiting'`, `confirm: { id, command, input }`) and waits for the hidden `assistant.confirm.reply`; declined calls return `MUTATION_DECLINED` to the model as an error result. A mutating assistant call made outside a chat has nobody to ask and is declined. Stopping the run or closing the project declines a pending confirmation.
- **Stopping:** `assistant.cancel` marks the chat `stopping` (announced) until the run has ended and, with Claude Code, the killed process has reported its exit (`whenStopped`); a call still running when the run ends is `stopped`. The composer stays disabled meanwhile.
- **Probes:** `assistant.probe { checking }` announces a Claude Code probe starting and ending, for the status bar's "checking Claude Code…"; `assistant.status` follows it.
- **Streaming to the window:** `assistant.event { projectId, event }`: `{ type: 'changed', state }` after every structural change (a message, a tool call starting or ending, a confirmation, the run ending, the session id), `{ type: 'text', id, delta }` for each piece of a streaming reply.

## Compliance

Checked against https://code.claude.com/docs/en/legal-and-compliance and https://www.anthropic.com/legal/aup on 2026-10-07; re-check both before shipping a build with this mode.

The Claude Code provider runs the user's own, unmodified Claude Code, installed and signed in by the user on this machine, as a subprocess. The app never reads, copies, stores or proxies its OAuth token or credentials file, never automates login (the empty state tells the user to run `claude` in a terminal and log in), and never calls the Messages API with a subscription token: it starts the binary and reads what it prints. Subscription use is personal: this mode is "bring your own Claude Code" for the person at the keyboard, it consumes their Claude Code usage limits (Anthropic's advertised limits assume ordinary individual use), and a hosted or multi-user build must use the API key path, which stays the default and the only supported path for anyone but the user. The only thing stored is the session id used to resume the chat, as view state in the project's `.local/ui.json` on this machine (never in the design, snapshots or exports); the per-process token in the MCP URL is not a credential of any kind. Anthropic's page says that OAuth sign-in is for the subscriber's own use of Claude Code and other native Anthropic applications, that developers building products should use API keys, may not route requests through Free, Pro or Max credentials on behalf of their users and may not collect, store or intermediate Claude.ai credentials or session tokens, and that an end user may sign in to the unmodified Claude Code binary with their own subscription; offering Claude Code inside a product requires the Commercial Terms and leaving the binary and its sign-in methods untouched. This mode does none of what is forbidden and relies on the last point; it is not a way to give other people Claude access.

## Storage

With the API provider, the chat lives in memory while its project is open and is dropped when the project closes or the app quits. With Claude Code, the chat is stored in the project's `.local/ui.json` under `assistant` (`{ provider, sessionId, items }`: the session id and the transcript, the last 200 items with tool inputs cut at 2 KB; this machine only, never the design, snapshots or exports), written when a run ends and when the project closes, and loaded when it opens while Claude Code is the provider (an API chat starts empty, the stored copy left alone), so a reopen or a restart shows the earlier chat and continues its session; history the stream replays on resume is then ignored. Clear removes the stored copy whichever provider runs. The API key is a secret (`host.secrets`, see the settings module), the model `config.ai.model`, the provider and the Claude Code path `config.ai.provider` / `config.ai.claudeCodePath`.

## Agents

Every command here is hidden: `assistant.status` (provider, key set, model, the MCP server, and for Claude Code found/version/logged in; `refresh` probes again), `assistant.state`, `assistant.image` (read-only: the image a tool call in the chat returned, kept in memory while the project is open and never stored or sent with the chat), `assistant.send`, `assistant.cancel`, `assistant.clear`, `assistant.confirm.reply`. Agents over MCP cannot drive the assistant or read its chat. The spawned Claude Code sees exactly the non-hidden commands, like any MCP agent, and its destructive calls wait for the user in the chat.

## Dependency

`@anthropic-ai/sdk`: the Claude API client (streaming, typed errors, the request and content types). External in the main bundle (it ships a CommonJS entry) and a root dependency, so electron-builder packages it. The Claude Code provider adds nothing: `node:child_process` and the app's own MCP server.
