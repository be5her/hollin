# Assistant

The in-app assistant: a chat with Claude inside the project tab, with every command of the app as its tools. Two providers, chosen in Settings > Assistant (`config.ai.provider`): the **Claude API** with the user's own key (the default, and the only path supported for anyone but the user), or the user's own installed, logged-in **Claude Code**, driven as a subprocess ("bring your own Claude Code", see Compliance below).

- **The panel** (`ui/assistant-panel.ts`, the Assistant tab of the project's right column): an empty state while the provider cannot run (no key; Claude Code not found; Claude Code not logged in, with a Check again button), otherwise the model's name (or "Claude Code <version>"), the transcript (the user's messages, replies streamed word by word, tool calls as cards with the command's title and, for a batch, its label, marked running, done, failed or declined), a confirmation card with Allow and Decline when a destructive command waits, the last run's error, Stop while a run goes, Clear, and a composer (Enter sends, Shift+Enter a new line). With Claude Code and the MCP server off, a notice with an "Enable MCP server" button sits above the composer. It loads `assistant.state` when it opens and follows `assistant.event`; replies are plain text.

- **Where it runs:** in the main process (`main.ts`). The API key never leaves main, tool calls run as `caller: 'assistant'` with the model id or the Claude Code version as the agent, and the question whether a destructive command may run is asked in the chat. The renderer only sees host events and a few hidden plumbing commands. `main.ts` keeps one chat per open project and picks a provider per run (`ChatProvider`: `send`, `stop`, `dispose`); both providers report through the same `LoopEvents` (`text`, `toolStart`, `toolEnd`, `note`), so the transcript, the cards and the events are the same whichever runs.

## The Claude API provider (`loop.ts`)

- **The loop:** one user message starts a run. Each round streams a reply (`client.messages.stream`); when the model asks for tools, every call runs through the registry and the results go back in one user message, until the model ends its turn, is stopped, or has used 25 rounds of tool calls. Image results (commands declared `output: 'image'`, i.e. `view.snapshot`) go back as image blocks, so the model sees the plan it changed. No `thinking` parameter is sent: the listed models think adaptively by default. `max_tokens` is 16,000.
- **Tools:** every non-hidden command, named as for MCP (`toolNameFor`: `plan.wall.add` is `plan_wall_add`), with its zod input as JSON Schema (`toolInputSchema`) and its description plus a note when it is gated. Hidden commands are never offered, and a tool name the model makes up is answered with an error result. Project tools act on the chat's project.
- **System prompt:** who the assistant is and how to work (read first, change in one `plan_apply` batch with a clear label, look at the result), `DESIGN_GUIDELINES` from core (the same text the MCP resource serves), then the live part: the project's name, its levels with ids and elevations, and the user's display units. The stable part carries a cache breakpoint.
- **Failures:** API errors end the run with a short reason (`error` in the chat state: a refused key, rate limiting, no connection); the API history is trimmed back to before the failed message, so the conversation never ends mid-round. Stopping a run (`assistant.cancel`) aborts the request the same way.
- **Pointing the SDK elsewhere:** the environment variable `STUDIO_AI_BASE_URL`, read when a run builds its client, replaces the API's base URL. The smoke test sets it to its fake API (`fake-api.ts`); it also serves a proxy. Never set in normal use.

## The Claude Code provider (`claude-code.ts`)

- **The binary:** `config.ai.claudeCodePath`, or `claude` on PATH (`findClaude`: a PATH and PATHEXT scan, never by image name). The native build is run directly; an npm install's `.cmd` shim is resolved to its `cli.js` and run through the app's own executable as Node (no shell is ever used); a `.js`/`.cjs` path (the fake) runs the same way. `assistant.status` probes it with `claude --version` and `claude auth status --json` (neither consumes usage), caches the answer per path, and probes again on `refresh` (the Check again button) or after a run that failed to authenticate.
- **One process per chat**, started on the first message and kept for the chat's life: `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --replay-user-messages --max-turns 25 --tools "" --mcp-config <the app's server only> --strict-mcp-config --allowedTools mcp__<server>__* --disallowedTools Bash,Edit,Write,Read,WebFetch,WebSearch --append-system-prompt <the same prompt the API provider sends> [--resume <id>]`, in `<data folder>/claude-code` (an empty folder the app owns, so no project CLAUDE.md is picked up). `--tools ""` removes the whole built-in set, so Claude Code can only act through the app's commands; the user's other MCP servers are never loaded. User turns go in as stream-json user messages; the reply's text deltas, the tool calls (`assistant` messages) and their results (`user` messages) come out as stream-json lines and become `text`, `toolStart` and `toolEnd`; the turn ends with Claude Code's `result`. Stop kills the process (`taskkill /pid <pid> /t /f` on Windows, SIGKILL elsewhere); the next message starts a fresh process that resumes the same session. Closing the project or quitting kills it too, and so does the MCP server stopping or moving (a note says so).
- **Tools over the app's own MCP server.** The server is never started by the assistant: while it is off (`config.mcp.enabled`), `assistant.send` is refused with `UNAVAILABLE` and the chat shows the notice with the "Enable MCP server" button, which runs the same `config.update` Settings uses, as the user's own click. The URL Claude Code gets is `http://127.0.0.1:<port>/mcp?project=<id>&assistant=<token>`: the token is 32 random bytes per process, kept only in this module's map while the process lives, never logged (call-log entries carry the tool, the agent and the project). The MCP server asks `host.identifyAssistant` (installed by this module) and, for a known token, runs the call as `caller: 'assistant'`, `agent: 'claude-code <version>'`, bound to the chat's project, inside the chat's `AsyncLocalStorage` scope, so edits show as "Assistant (claude-code …)" in History and mutating calls go through the chat's Allow/Decline card, not the Settings > MCP switch. Any other MCP client stays `caller: 'mcp'`, token or not. The token sits in the process's command line, visible to the same user on this machine, which is the audience the loopback server already has.
- **Resume.** The session id from Claude Code's `init` event is stored per project in the project's per-machine view state (`assistant.sessionId` in `.local/ui.json`, through `host.projects.setUiState`, which merges keys: not in the design, not in snapshots or exports) and passed as `--resume <id>` whenever a process is started for that chat again: after Stop, after the project is reopened, after the app restarts. Everything the stream prints before the echo of the turn's own message (`--replay-user-messages`) is the resumed session's history and is rebuilt into the transcript before the new message, unless the transcript was restored from the view state (see Storage), which is the normal case; Claude Code 2.1 itself replays nothing on resume, the fake does. A resume that fails (the session was deleted, Claude Code was reinstalled: the process dies before its first result) forgets the id, says so in the chat as a note and starts a new session with the same message. Clear kills the process, forgets the id and starts a new session next time.
- **Failures:** a process that exits mid-turn, a `result` with `is_error`, or an MCP server Claude Code could not connect to end the run with the reason as the chat's error. A logged-out Claude Code answers the first turn with "Failed to authenticate…" (checked against 2.1.283); the status is marked not logged in and the panel shows the matching empty state.
- **Checked against the real binary** (2.1.283, logged in, 2026-10-07, by hand, never by the tests or the smoke): `init` lists the app's server as `connected` and the `mcp__plan-studio__*` tools as the only tools; the wildcard in `--allowedTools` is honoured in `-p` mode, so a tool call runs without a permission prompt; the echo of a stdin turn carries `isReplay: true`; a text block's `assistant` message arrives before the `tool_use` one; a tool result's `content` is an array of text blocks; a second process started with `--resume <id>` continues the session (it answered from the earlier turn) and replays nothing. The environment variable `STUDIO_CLAUDE_CODE_LOG=<file>` makes the provider append every line Claude Code prints (stdout and stderr) to that file, for looking at a conversation that went wrong; never set in normal use.

## Attribution, undo and confirmation (both providers)

- Every edit the assistant makes is a transaction with the command's own label and the author `{ kind: 'assistant', name: <model id or claude-code version> }`, so the History panel shows "Assistant (claude-…)" and one Ctrl+Z undoes a whole `plan.apply` batch.
- Mutating commands (deletes, writes outside the library) reach `host.confirmMutation`, which this module installs when it starts. It finds the chat the running tool call belongs to (an `AsyncLocalStorage` around each call, and around each recognised MCP call), puts the request in the chat (`status: 'waiting'`, `confirm: { id, command, input }`) and waits for the hidden `assistant.confirm.reply`; declined calls return `MUTATION_DECLINED` to the model as an error result. A mutating assistant call made outside a chat has nobody to ask and is declined. Stopping the run or closing the project declines a pending confirmation.
- **Streaming to the window:** `assistant.event { projectId, event }`: `{ type: 'changed', state }` after every structural change (a message, a tool call starting or ending, a confirmation, the run ending, the session id), `{ type: 'text', id, delta }` for each piece of a streaming reply.

## Compliance

Checked against https://code.claude.com/docs/en/legal-and-compliance and https://www.anthropic.com/legal/aup on 2026-10-07; re-check both before shipping a build with this mode.

The Claude Code provider runs the user's own, unmodified Claude Code, installed and signed in by the user on this machine, as a subprocess. The app never reads, copies, stores or proxies its OAuth token or credentials file, never automates login (the empty state tells the user to run `claude` in a terminal and log in), and never calls the Messages API with a subscription token: it starts the binary and reads what it prints. Subscription use is personal: this mode is "bring your own Claude Code" for the person at the keyboard, it consumes their Claude Code usage limits (Anthropic's advertised limits assume ordinary individual use), and a hosted or multi-user build must use the API key path, which stays the default and the only supported path for anyone but the user. The only thing stored is the session id used to resume the chat, as view state in the project's `.local/ui.json` on this machine (never in the design, snapshots or exports); the per-process token in the MCP URL is not a credential of any kind. Anthropic's page says that OAuth sign-in is for the subscriber's own use of Claude Code and other native Anthropic applications, that developers building products should use API keys, may not route requests through Free, Pro or Max credentials on behalf of their users and may not collect, store or intermediate Claude.ai credentials or session tokens, and that an end user may sign in to the unmodified Claude Code binary with their own subscription; offering Claude Code inside a product requires the Commercial Terms and leaving the binary and its sign-in methods untouched. This mode does none of what is forbidden and relies on the last point; it is not a way to give other people Claude access.

## Storage

With the API provider, the chat lives in memory while its project is open and is dropped when the project closes or the app quits. With Claude Code, the chat is stored in the project's `.local/ui.json` under `assistant` (`{ provider, sessionId, items }`: the session id and the transcript, the last 200 items with tool inputs cut at 2 KB; this machine only, never the design, snapshots or exports), written when a run ends, on Clear (which removes it) and when the project closes, and loaded when it opens, so a reopen or a restart shows the earlier chat and continues its session; history the stream replays on resume is then ignored. The API key is a secret (`host.secrets`, see the settings module), the model `config.ai.model`, the provider and the Claude Code path `config.ai.provider` / `config.ai.claudeCodePath`.

## Agents

Every command here is hidden: `assistant.status` (provider, key set, model, the MCP server, and for Claude Code found/version/logged in; `refresh` probes again), `assistant.state`, `assistant.send`, `assistant.cancel`, `assistant.clear`, `assistant.confirm.reply`. Agents over MCP cannot drive the assistant or read its chat. The spawned Claude Code sees exactly the non-hidden commands, like any MCP agent, and its destructive calls wait for the user in the chat.

## Dependency

`@anthropic-ai/sdk`: the Claude API client (streaming, typed errors, the request and content types). External in the main bundle (it ships a CommonJS entry) and a root dependency, so electron-builder packages it. The Claude Code provider adds nothing: `node:child_process` and the app's own MCP server.
