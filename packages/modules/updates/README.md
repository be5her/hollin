# Updates

In-app updates (milestone 10): the app finds a new version on its GitHub Releases, downloads it when the user asks and installs it when the user restarts. Nothing is downloaded or installed without the user.

## What it does

- **The updater is a host service**, like the dialogs. `src/main/updater.ts` wraps `electron-updater`'s `autoUpdater` (`autoDownload: false`, `autoInstallOnAppQuit: true`), or in an AppImage an `AppImageUpdater` it makes itself (see below), behind the host's `Updater` (`src/main/update-state.ts`); the host takes it in its options (`HostOptions.updater`), hands it to commands as `host.updater` and announces each change as `update.changed`. The smoke passes a scripted one instead (`src/main/smoke/updater.ts`), so no smoke run reaches the network or quits.
- **One state record** (`UpdateState` in core): `idle`, `checking`, `available` (with `version` and `notes`), `up-to-date`, `downloading` (`progress`, 0 to 100, announced once per whole percent), `ready`, `error` (`message`: the error's first line) or `unsupported` (`message`: why), with `checkedAt` (the last check that reached the feed) and `scheduled` (that check was the startup one). What may follow what lives in `UpdaterBase`, shared by the real and the scripted updater: a check while one runs, while downloading, after a download is ready or in an unsupported build does nothing; a download needs a version found; an install needs a download ready, and a second install asked for while one runs (the toast and the button, a double click) waits for that one instead of starting the installer again (electron-updater would). A check or download still running when the updater starts over (`restart`: the smoke's `reset()`, or the build turning unsupported) ends without touching the newer state. Failures of the feed, the download or the installer become `state: 'error'`, never a thrown error or a crash.
- **Release notes** are kept as plain text: the GitHub provider gives the release body as HTML, so `plainNotes` drops the tags (scripts and styles with their content), turns `<br>`, block ends and list items into lines (`- ` for an item), decodes entities and squeezes blank runs. The UI shows them as text, never as HTML.
- **When this build cannot update** (`unsupported`), read from electron-updater 6's own rules (`updateSupport`, unit-tested):
  - a development run (not packaged), unless a `dev-app-update.yml` sits in the app path, electron-updater's own way to test updates in development (`forceDevUpdateConfig`);
  - no `app-update.yml` under `process.resourcesPath`: electron-builder writes it only when the build has a `publish` feed, which only the release workflow sets, so a local `npm run package` has none;
  - Linux, when the app runs neither from its AppImage (`APPIMAGE` is not set) nor as an installed package: electron-updater 6 updates a deb, rpm or pacman install too (`DebUpdater` and the others, chosen by the `package-type` file electron-builder writes into a package's resources; it installs with `pkexec`/`sudo` and `dpkg`), so the `.deb` is supported, not excluded. `APPIMAGE` is looked at first: electron-builder packs the AppImage from the same `linux-unpacked/resources` its deb target writes `package-type` into, in parallel, so an AppImage may carry the deb's file, and `autoUpdater` (which reads `package-type` before `APPIMAGE`) would then update the AppImage through dpkg. So in an AppImage the app makes an `AppImageUpdater` itself and never reads `package-type`, and the release workflow fails a Linux build whose AppImage carries the file;
  - macOS, when the app is not signed with a Developer ID (`codesign -dv` shows no `TeamIdentifier`, or `Signature=adhoc`): Squirrel.Mac installs only into a signed app.
- **The scheduled check:** 10 s after the window has loaded and then once a day while the app runs (`scheduleChecks` asks every hour, the check runs when the last one is a day old), only in a packaged run (never in development or the smoke), only when `config.updates.check` is on (the default), never once the app is stopping, and at most once a day: the time of the last check that reached the feed is kept in `updates.json` in the app's data folder (not in config, written atomically), and a failed check does not count, so the next start tries again. It only announces what it found: a toast `Version x is available` with **Settings**, which opens Settings at Updates.
- **Beta versions** (`config.updates.beta`, off by default): every check, the user's and the scheduled one, passes the setting as `check({ beta })`, and the real updater sets electron-updater's `allowPrerelease` from it before asking (electron-updater would otherwise turn it on by itself in a build whose version has a pre-release part). With it on, the GitHub provider reads the releases feed and offers the newest published release, pre-release or not (`beta` or `alpha` channels only); off, only the latest stable release. Turning it off never downgrades: `allowDowngrade` stays off, so a beta installed stays until a newer stable version is out. A beta is a GitHub pre-release made from a `v<x.y.z>-beta.<n>` tag (`docs/release.md`).
- **Installing** goes through the same orderly stop as quitting (`stopForQuit` in `src/main/index.ts`): the host saves the projects and lets queued writes finish (`Host.stop`, idempotent), then `quitAndInstall(true, true)` installs silently and starts the new version; `before-quit` then lets the quit through. Once the stop has begun, any failure (the stop itself, `quitAndInstall` throwing, or the installer reporting an error) sets the error and restarts the app into the version it has (`installAfterStop` and `installFailed`), since its host is stopped; the real updater applies once per run. A downloaded update the user did not install now installs when the app quits (`autoInstallOnAppQuit`).

## UI (`ui/`)

- **Settings > Updates**, after the Assistant and just before About (`SettingsSections` with `order: SETTINGS_LATE`): the state as one line (`data-testid=updates-status`, its `data-state` the state): `Not checked yet` or `Last checked …`, `Checking…`, `Version 1.2.3 is available`, `You have the latest version (checked …)`, `Downloading 42 %`, `Ready to install version 1.2.3. It also installs when you quit.`, the error's message, or `Updates are not available in this build: <reason>`. Then **Check for updates** (`updates-check`; enabled when idle, available, up to date or after an error), **Download** (`updates-download`; enabled only when a version is available) and **Restart and install** (`updates-install`; enabled only when ready), the release notes under `What's new in <version>` as plain text (`updates-notes`), the checkbox **Check for updates when the app starts** (`updates-auto`, `config.updates.check`), and **Get beta versions** (`updates-beta`, `config.updates.beta`) with its note (`updates-beta-note`). Changing the beta switch while the last check found a version or found none checks again, since that answer came from the other channel. The section asks `app.update.status` once when it opens and then takes each state from the `update.changed` payload (`injectHostEvent`), so a download's hundred progress steps cost no round trips.
- **Toasts** (`UpdateNotices`, started at setup): a version found by a scheduled check (`Version 1.2.3 is available`, action **Settings**), and a download that is ready (`Version 1.2.3 is ready to install`, action **Restart and install**). A check the user started shows its outcome in Settings and gets no toast. Toasts with an action stay 6 s.

## The feed and signing

- **The feed is the repository's GitHub Releases**, set by the build: `electron-builder.cjs` sets `publish` to `{ provider: 'github', owner, repo, releaseType: 'draft' }` only when `GITHUB_REPOSITORY` is in the environment (every GitHub Actions run, so the release workflow), and to `null` otherwise (left out, electron-builder would guess a GitHub feed from a `GH_TOKEN` in the environment). With a feed, electron-builder writes `app-update.yml` into the build's resources (and `package-type` into a deb's) and a `latest.yml`, `latest-mac.yml` or `latest-linux.yml` beside the installers, from the targets electron-updater installs: NSIS, the macOS zip (the dmg listed beside it), AppImage and deb. `generateUpdatesFilesForAllChannels` is off: one channel, `latest`, also in a beta (on GitHub the pre-release flag is what makes it one). electron-updater reads the latest published release: drafts are never offered, pre-releases only with beta versions on.
- **Signing** switches on with its secrets (`docs/release.md`): Windows through `WIN_CSC_LINK`/`WIN_CSC_KEY_PASSWORD`, after which electron-updater checks that an update's installer carries the same publisher before installing it; macOS through the `MAC_CSC_LINK`/`MAC_CSC_KEY_PASSWORD` secrets, which the workflow passes to the macOS job only, as `CSC_LINK`/`CSC_KEY_PASSWORD` (hardened runtime, `resources/entitlements.mac.plist`), notarized when `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD` and `APPLE_TEAM_ID` are set. A secret that is not set arrives empty: electron-builder treats an empty `WIN_CSC_LINK` as unset, but on macOS it would take an empty `CSC_LINK` as a certificate, so `electron-builder.cjs` maps it to `identity: null`. Unsigned, Windows and Linux builds still update; a macOS build does not (Squirrel.Mac needs a signed app), which `updateSupport` reports as `unsupported`.

## Storage

`updates.json` in the app's data folder holds `{ checkedAt }`. `config.updates.check` and `config.updates.beta` are in `config.json`. electron-updater keeps its download in its own cache folder (`<name>-updater` under the OS cache) and removes it after installing.

## Agents

None. Every command here is **hidden**: an agent must never be able to download or install code, so none reaches the palette, the MCP server or the assistant's tools. That is the real protection: a hidden command is no MCP tool, so an MCP client calling `app_update_install` or `app_update_download` by name gets an unknown tool. `download` (it writes an installer outside the library) and `install` are also `mutating`, a second line: `execute` runs hidden commands for any caller (the UI and the smoke call them), and an MCP or assistant caller naming either through it is refused with `MUTATION_BLOCKED`.

- `app.update.status`: the `UpdateState`.
- `app.update.check`: asks the feed (betas too when `config.updates.beta` is on); returns the outcome (`up-to-date`, `available`, `error`, or the state unchanged when a check cannot run).
- `app.update.download`: starts the download and returns at once (`downloading`); progress and the end follow as `update.changed`. `CONFLICT` when no version was found.
- `app.update.install`: stops the app, installs and restarts. `CONFLICT` when no download is ready.

`app.info` (visible) carries `updates: boolean`: whether this build can update itself.

## Dependency

`electron-updater` (`^6.8.11`, a runtime `dependency`: main requires it when the app runs): in-app updates from GitHub Releases, asked for by the brief. It stays **external** to the main bundle (listed in `external` in `electron.vite.config.ts`, which electron-vite 5 would also do by itself for a `dependency`): a build with it bundled works (about 570 kB more in `out/main/index.js`, no warnings), but electron-builder packages every `dependency` from `node_modules` anyway, so bundling would ship it twice, and every other runtime dependency is loaded the same way. electron-updater loads `electron` itself, which is never bundled.
