# Working on Hollin

Hollin (every product name lives in `branding.json`) is a desktop studio for designing buildings, floor plans, interiors and decor, with AI built in: Electron + an Angular renderer in an npm-workspaces monorepo. `README.md` is the overview; `packages/core/README.md` covers the engine and storage, `src/renderer/README.md` the shell, and each module has its own README under `packages/modules/<name>/`. This file is about how changes get made.

## Workflow

- The repository is public on GitHub, `be5her/hollin`, under the MIT licence (`LICENSE`; the name, Otto and the logo are not part of it). Work on it through the `be5her` account (`gh auth switch --user be5her` when another account is active).
- One branch and one pull request per change, against `main`. Never commit to `main`. Open the pull request with `gh pr create` following `.github/pull_request_template.md`, report the link and do not merge. CI (`.github/workflows/ci.yml`) runs the typecheck, the unit tests and a build on Linux and the full smoke on Windows for every pull request and every push to `main`.
- Before every commit, all three must pass: `npm run typecheck`, `npm test`, `npm run smoke`.
- For UI changes, run the smoke with `SMOKE_SHOTS=<dir>` and look at the screenshots (light and dark) before committing.
- Each module has a README covering what it does, what it stores, which tools agents may call and which are gated, and what the smoke test covers. Update it when behaviour changes.
- No new dependency without a one-line reason, in the commit message and in the README of the package that uses it.
- Keep the clone's author identity on commits.
- Releases (`docs/release.md`): the version in `package.json` and its `CHANGELOG.md` section change with the change that warrants them (user-visible changes go under `## [Unreleased]` until a release names them). Tags, the GitHub repository's settings and its secrets are the owner's: never tag. The update feed comes from `GITHUB_REPOSITORY` at build time, never from the source; `package.json`'s `homepage`, `repository` and `bugs` name the repository as metadata only (npm, the deb's homepage). `release.yml` uploads to a draft release, which the owner publishes.

## Conventions

- **Everything is a command.** A feature is a set of registry commands (`defineCommand` with a zod input schema, grouped by `defineModule`) plus UI. Commands are the only way the UI reaches the host, so the command palette, the MCP server and the in-app assistant get every feature for free. Write each command's `description` for an agent: what it does and what it returns.
- **Mutating** means deletes, writes outside the library, or is otherwise destructive (`mutating: true`, or a function for per-call decisions). MCP agents are refused those until the user allows mutations; the assistant asks the user. Ordinary design edits are not mutating: they are undoable transactions.
- **Read-only** (`readOnly: true`) marks a command that changes nothing at all: a query, a description, a list, a probe, a snapshot. MCP gives it `readOnlyHint` (and `destructiveHint` from `mutating`). An ordinary edit is neither read-only nor mutating; a command cannot be both (registering one throws).
- **Hidden** commands are UI plumbing and never reach the palette or agents. Anything that could let an agent widen its own permissions (`config.update`, secrets) is hidden.
- **Every change the UI shows must be announced.** Add the event to `HostEvents` in `packages/core/src/types.ts` and emit it after the write; the UI follows with `invokeResource(..., { refreshOnEvents })` or `injectHostEvent`. Otherwise a view only catches up when it is reopened.
- **Storage:** atomic writes only (`writeFileAtomic`: temp file, fsync, rename with a retry for Windows locks), serialized per file with `WriteQueue`. Lengths are millimetres everywhere; display units are a setting. Secrets go through `host.secrets` and never into config, projects or exports.
- **Modules:** `packages/modules/<name>/main.ts` (Node side, registered in `packages/modules/main.ts` and listed in `tsconfig.node.json`'s globs), `ui/` (Angular side, registered in `packages/modules/ui.ts`; `src/renderer/tsconfig.app.json` picks it up), `README.md`.
- **Renderer:** current Angular defaults only: standalone components, zoneless, OnPush, signals, signal inputs/outputs/`model()`, `viewChild()`, built-in control flow, `host` metadata, `inject()`, `@Service()`, Signal Forms (`[formField]`; editors with several fields implement `FormValueControl`). No experimental APIs. Shared controls are attribute directives on native elements (`button[xButton]`, `input[xInput]`, `select[xSelect]`). Colours are the semantic variables in `src/renderer/src/styles.css`, never raw values.
- **Smoke test:** new behaviour gets checks in `src/main/smoke/` (one file per area) that drive it through commands, through MCP and through the UI. Unit tests sit next to pure code in `packages/*`.
- **Line endings** are LF everywhere (`.gitattributes`).

## Gotchas

- The Angular compiler needs TypeScript 6.0, pinned in `src/renderer`; the root uses TypeScript 7 for main, preload and the packages.
- Signal Forms types a checkbox only when `type="checkbox"` is written in the template, even with `xCheckbox`.
- A `[formField]` element may not set `name`, `min` or `max` itself (NG8022 at compile time): radios of one field need no `name`, and limits are `min()`/`max()` validators in the form's schema. Write `type="radio"` in the template as well: with a bound `[type]` the radio's `value` attribute is refused too.
- `npm run dev` uses a separate data folder (`<name> Dev`); the smoke test uses a temporary one and a private MCP port. Neither touches the real library.
- On Windows, write multi-line scripts with a file rather than a shell heredoc, and stop processes by PID (`taskkill /pid <pid> /t /f`), never by image name.
- `packages/viewport` is type-checked by `tsconfig.node.json` (its unit tests run in node, so nothing there may touch `ResizeObserver`, `OffscreenCanvas` or `Path2D` at import time) and compiled into the renderer through its imports.
- The plan canvas mirrors its state into `data-camera="x,y,scale"`, `data-level`, `data-underlay`, `data-entities`, `data-frame-level` (the level the last frame drew) and `data-frame-ms`; the smoke test converts millimetres to window pixels from those and samples pixels with `canvasPixel`. Measure the canvas rect again after switching tools: a tool's options bar changes the canvas height, so screen positions computed before it appeared (or vanished) are off by half its height. The canvas follows the theme by watching `<html class>`, so the smoke's `setDark` works without going through the app's theme service.
- In the smoke harness, `typeText` sends `char` events only: a key a canvas must see goes through `key()`, and the first character typed into a just-focused input too. `wheel()` takes the DOM's sign (negative zooms in).
- `clipper2-ts` is pinned exactly to `2.0.1-18` (its releases are `2.0.1-N`; a caret installs the old plain `2.0.1`). It is ESM-only, so it must never be added to the `external` list in `electron.vite.config.ts`: main's CommonJS bundle would `require()` it. Keep it in `packages/core` and let electron-vite bundle it.
- Derived geometry memoised by object identity (`LevelGeometryCache`) is valid in the renderer only: the mirror builds a fresh draft per patch. In main, a transaction mutates a level's entity record in place while a `plan.apply` batch runs, so main derives afresh (`deriveLevelGeometry`).
- Points are readonly tuples (`Vec2 = readonly [number, number]`) in both the geometry and the zod schemas; build new points instead of mutating.
- Project thumbnails are drawn in the renderer (`renderLevelToPng`, the ground floor) 1.5 s after a project's last change and when its tab is left, and stored through the hidden `project.thumbnail.set`. A smoke section's edits can therefore land a thumbnail during a later section; checks that compare library summaries should ignore `thumbnail`. `view.snapshot` draws in the renderer the same way, through a `view.snapshot.request` event answered by the hidden `view.snapshot.reply`: it needs the window, so its smoke checks belong in the UI phase (after `smoke.openWindow`), and a command declared `output: 'image'` must return `{ mimeType, data }` (base64) for MCP and the assistant to pass it on as an image.
- Toasts stack over the bottom-right corner of the window. A smoke step that right-clicks (or clicks) something there, such as the last Home card, must dismiss them first (`rightClickCard` in `src/main/smoke/library-ui.ts`) or aim away from that corner. The smoke window is only about 780 px tall: a Home card on the second row is below the fold, so scroll it into view before a real click (`rightClickCard` does). Every project an earlier smoke section creates adds a card.
- The plan canvas helpers for the smoke (`readCamera`, `toScreen`, `view`) live in `src/main/smoke/plan-canvas.ts`; measure `view()` again after anything that changes the canvas. `data-level` follows the switcher before the next frame is drawn: a pixel probe after a level switch waits for `data-frame-level` (it once sampled the old floor, which looked like a missing stairwell). The switcher's options appear once the document has arrived, so a `fill` of `plan-level` right after a tab opens must first wait for the level's `option`, or the value is dropped.
- Angle tracking is on by default, so a smoke gesture near a main angle or near parallel or perpendicular to a wall snaps to it; a click or drag that must land where the pointer is holds Alt (as the connector drags do), and a check that expects a free angle must aim well away from every tracked ray: more than 3° off it (a quarter of the step when finer) however far the pointer is from the start, and more than the pixel tolerance near it.
- `hidden` is metadata only: `execute` runs hidden commands for any caller. The MCP server and the command palette filter on it, and so must anything else that offers commands to an agent (the assistant builds its tool list from `host.listCommands()` filtered on `hidden`). The assistant never calls the real API in the smoke or the unit tests: `STUDIO_AI_BASE_URL` points the SDK at `packages/modules/assistant/fake-api.ts`, which streams scripted turns; a run's chat is found by `AsyncLocalStorage` around each tool call, so a mutating call made as `caller: 'assistant'` outside a chat is declined (`MUTATION_DECLINED`), not blocked.
- The assistant's Claude Code provider (`packages/modules/assistant/claude-code.ts`) spawns the user's own `claude` as a subprocess whose only tools are the app's commands over the app's MCP server (`--tools ""`, `--strict-mcp-config`, the URL carrying `?assistant=<per-process token>` which `host.identifyAssistant` turns into `caller: 'assistant'`). The real binary is never run by the tests or the smoke: `config.ai.claudeCodePath` points at `fake-claude.cjs` (scripted through `FAKE_CLAUDE_SCRIPT`, logging to `FAKE_CLAUDE_LOG`, logged out with `FAKE_CLAUDE_LOGGED_OUT`), which a `.cjs` path runs through the app's own executable as Node; the smoke carries the fake into the packaged build as a Vite `?raw` import (`src/main/raw.d.ts` declares it) and writes it to its data folder. Kill the process by pid only (`taskkill /pid … /t /f`); a killed process reports its exit a little after the OS has it gone, so the provider waits for that before starting the next one. The real binary was checked by hand once (2.1.283, see the module README); to see what a real conversation printed, set `STUDIO_CLAUDE_CODE_LOG=<file>` before starting the app. The session id for `--resume` lives in the project's view state; the app never touches Claude Code's credentials (see the module README's Compliance section).
- A project's per-machine view state (`.local/ui.json`, `project.ui.get`/`project.ui.set`) is shared between the renderer (active level, camera, panels) and main (the assistant's Claude Code session): `setUiState` merges key by key (`null` removes a key) and the renderer's `ProjectView` sends only the keys it changed, so neither side can wipe the other's keys. Never write the whole record back.
- Main modules subscribe to host events with `host.on` (`HostApi`), e.g. the rules watcher on `doc.patched`; it recomputes 250 ms after the last change and announces `rules.changed` only when the set of warnings differs, so a smoke check waits for the event or the panel, never for a fixed delay. A panel that wants the plan to select something goes through `PlanSelection.request` (the plan applies it once its level matches), because `editor.setLevel` clears the selection.
- Tool shortcuts: single letters pick tools (V W D N R S P K O L T E C I G) and Shift+S, Shift+R, Shift+L, Shift+E the stair, ramp, ladder and escalator (check the shifted letters before the plain ones: `E` is the elevator); a tool's `key` runs first, which is how `C` edits a selected corner but places a column otherwise. Every tool with an options bar changes the canvas height: measure `view()` again after picking one (the stair, ramp, ladder, escalator, elevator and column bars included).
- Connectors have no layer and are not entities: `plan.path.*`, `plan.transform`, `plan.entity.delete` and `plan.query` accept their ids next to entity ids and tell them apart by the id prefix (`str_`, `elv_` ..., `isConnectorId`); a path edit on a connector takes only `which: 'outer'` (the walk line). They are always drawn and selectable, and both marquee modes take them, so a smoke marquee over a level a stair arrives at selects the stair too.
- A single synthetic pointer move is not guaranteed to reach the canvas before the next step under load (it once left the angle-tracking and footer checks failing one run in three, while the owner's dev app was running). A check that depends on what a hover shows (the snap footer, the cursor position) moves the pointer again, a pixel aside and back, until the footer says it (`moveUntil` in `src/main/smoke/tracking-ui.ts`), rather than moving once and waiting.
- `smoke.until` returns false on a timeout instead of throwing: a wait whose result is not checked lets the section go on in the wrong state (that is how a dropped level switch looked like a missing stairwell). `console.warn` in the renderer lands in the smoke log as `[renderer:warning]`, the quickest way to see what a frame had.
- Pointer positions reach the page as whole pixels (`Math.round` in the harness), so a smoke check that expects an exact millimetre result from a drag only holds while the fit zoom happens to map that point onto a pixel. Anything that changes the canvas height (a toolbar row, an options bar) changes the fit zoom: compare drag results within a pixel's worth of millimetres (`1 / cam.scale`) or against the geometry actually drawn, never to a hardcoded exact value.
- The 3D view's canvas is WebGL, so a 2D context cannot sample it. The smoke projects building points (mm, z up) to window pixels through the view-projection matrix the view mirrors in `data-camera3d` (`sceneView` in `src/main/smoke/scene-canvas.ts`) and reads the window's capture there (`screenPixel`); measure again after a preset, a fit, a mode change or anything that resizes the canvas. A gesture is checked against `data-orbit`, `data-levels`, `data-clip` or `data-walk`, never a fixed wait. The smoke launches with `enable-unsafe-swiftshader` so WebGL works on a machine without a GPU (CI); real runs keep Chromium's default. A page holds few WebGL contexts: a renderer made for one picture (`renderBuildingToPng`) is disposed with its context lost.
- After `project.open` the window activates the project's tab only after the event's round trip: a click inside the tab right away can land on the tab that was showing (the assistant sections once missed their panel that way). Use `openProjectTab` (`src/main/smoke/plan-canvas.ts`), which waits until the visible tab shows the project's name.
- The performance bounds (`perf.test.ts`: 2 s for 5,000 walls; `solids.test.ts`: 5 s to build them in 3D; `smoke/perf.ts`: a 100 ms mean frame on the plan, 250 ms in 3D, also for 200 items and 20 lights at night) are loose because CI draws with software GL. Read the logged numbers, not only the pass.
- `project.json` is format 2: the project's asset registry (`assets`, keyed by `<sha256>.<ext>`) came with decor, and a format 1 file is migrated (an empty registry) after an automatic snapshot. References follow one grammar (`packages/core/src/decor/refs.ts`): `builtin:<id>`, `asset:<sha256>.<ext>`, `paint:#rrggbb`; the schema checks the form where items, finishes, wall faces and styles take them, and the transaction checks that every `asset:` an item uses is registered (`refsOf` has `asset` targets, never remapped). Placing a library model copies the file into the project's `assets/` outside the transaction, then registers it inside: an orphan file left by a failed edit is harmless (content-addressed). Built-in ids are stored in projects: rename a recipe's `name`, never its `id` (`builtin.test.ts` pins them).
- The library catalog is `catalog/furniture/<sha256>.glb` with a rebuildable `index.json` (`packages/core/src/node/catalog.ts`); removing a model never touches projects. `library://` serves only what `libraryUrlFile` (core) allows: project thumbnails and assets, catalog models and thumbnails; add a path there, with a unit test, never in the protocol handler.
- GLB reading and writing live in core without a library (`decor/glb.ts`): tests and the smoke make their models with `writeGlb`/`meshToGlb` (`smokeTableGlb` in `src/main/smoke/decor.ts`). glTF is metres with y up, the app millimetres with z up: (x, y, z) → (1000 x, −1000 z, 1000 y), so a model's front faces −y, as a recipe's does.
- At night the 3D view switches on only the 16 lights nearest the camera (`MAX_LIGHTS` in `scene3d/view.ts`), and only when that set changes, since three rebuilds its shaders whenever the number of lights does; the canvas mirrors `data-lighting` and `data-lights` (how many are on). `renderBuildingToPng` is async: it waits for the imported models the design shows.
- The plan's hit-test finds a detected room only near its seed (its index box is a square there); a tool that needs the room anywhere in its space (the Paint tool) asks the level geometry (`roomAt`) instead.
- A tool picked from another panel (the Catalog arming Furniture or Paint) may arrive before the plan view has its canvas: the plan view announces the editor's current tool at mount instead of resetting it to Select, and leaving the Paint tool (a transition, not any report of Select) is what ends painting. Every tool with an options bar (Furniture, Light, Paint included) changes the canvas height: measure `view()` again after it appears and after Escape removes it.
- After `assistant.cancel` a chat is `stopping` (in `ChatSnapshot`) until the run has ended and a killed Claude Code process has reported its exit; the composer is disabled meanwhile, so a smoke `send` helper waits for `status === 'idle' && !stopping`, not for idle alone. To look at the app while Otto is "thinking", script a fake API turn with `hold: true` and let it go with `fake.release()` (waiting on `fake.held`), never a delay. Otto's state on the status bar is `status-otto` with `data-state` (`AppState.assistant`, published by `OttoPresence` in the assistant module's UI).
- The assistant's Claude Code smoke spawns the fake through the app's executable: on a busy machine a probe, a kill (`taskkill /t /f`) or a respawn can take many seconds. Its checks wait on the condition itself (the probe's answer through `assistant.status`, the pid gone, the reply shown) with a 30 s budget; keep new waits of that kind the same.
- Smoke runs never open a native dialog: `app.pickFile`, `app.pickSavePath` and `app.pickFolder` answer with the next path queued by `smoke.nextDialogPath(path)`, cancelled when nothing is queued, and every pick is recorded with its options in `smoke.dialogs.asked` (`app.revealPath` in `smoke.dialogs.revealed`). Queue the answer before the click that opens the picker, and check `asked` for the filter and default name.
- The project tab's toolbar (Export…, Import DXF…, the Layers panel) exists once per open project tab, the hidden ones included: a smoke click on it is scoped with `${tab}` from `src/main/smoke/plan-canvas.ts`, or it can land on a tab that is not showing.
- A toast with an action (an export's Show) stays 6 s, like an error; the others 3 s. A step that clicks the action must do so within that time, and one that clicks near the bottom-right corner dismisses the toasts first.
- The PDF writer (`exchange/pdf.ts`) assembles the file as bytes because the xref holds byte offsets and the deflated content streams are binary: counting string characters instead (or encoding a string afterwards, where `²` is one WinAnsi byte but two in UTF-8) shifts every offset after it, and readers then rebuild or refuse the file. In DXF, a bulge is tan(sweep / 4) and positive for a counter-clockwise arc, and an ARC always runs counter-clockwise (a clockwise one is written from its end).
- The plan's symbols (door swings, window glazing, dimension ticks, walk lines, arrow heads, the break line, glyph sizes) are geometry in core (`geometry/plan-symbols.ts`, `openingSymbol`, `dimensionMarks`) shared by the canvas and the plan exports: change a symbol there, never in the renderer alone, or the DXF, SVG and PDF stop matching the screen.
- `export.image` and `view.snapshot` refuse a 3D render WebGL could not draw at the asked size (the drawing buffer is capped by the GPU): `renderBuildingToPng` throws `SnapshotSizeError`, the window answers `UNAVAILABLE`, and main checks the PNG's IHDR against the size too. Never return or write a smaller image; the smoke accepts either outcome at 4096 × 4096 and logs which.
- The 3D render palette's kind colours (`LIGHT_SCENE_THEME`) and the glTF export's both come from core's `SOLID_COLORS` (`exchange/gltf.ts`), but the 3D view in the window reads `--scene-*` from `styles.css`, whose `:root` values repeat them: change a kind's colour in both places. `snapshot-theme.test.ts` checks the light palettes (`LIGHT_THEME`, `LIGHT_SCENE_THEME`, `SOLID_COLORS`) against the `:root` block and the dark ones against the `.dark` block.
- The smoke never runs electron-updater: `src/main/index.ts` hands the host a scripted updater (`src/main/smoke/updater.ts`, reached as `smoke.updates`: `script`, a `hold` let go by `release()`, `unsupported`, `installs`), and a section that scripts it ends with `reset()`. The startup check never runs in development or the smoke (the smoke returns before it is scheduled), so the startup toast is checked by calling `smoke.updates.check({ scheduled: true })` directly.
- The `app.update.*` commands are hidden (an agent must never download or install code; hidden commands are no MCP tools, which the smoke checks by calling `app_update_install` by name) and `download` and `install` are also mutating. Installing stops the host through `stopForQuit` in `src/main/index.ts`, the one orderly stop shared with `before-quit` and Windows logoff, before `quitAndInstall`; a new way to leave the app goes through it too. `UpdaterBase.install` hands a second ask the install already running (electron-updater would start the installer twice), and once the stop has begun any failure relaunches the app (`installFailed` in `src/main/updater.ts`): the host is stopped. A step that starts the updater over (the smoke's `reset()`) goes through `restart`, so a check or download still running cannot overwrite the newer state.
- On Linux electron-updater's `autoUpdater` reads `resources/package-type` before `APPIMAGE`, and electron-builder packs the AppImage from the folder its deb target writes that file into, in parallel: an AppImage may carry the deb's `package-type` and would then update through dpkg. So `updateSupport` looks at `APPIMAGE` first and `src/main/updater.ts` makes an `AppImageUpdater` itself in an AppImage (`autoUpdater` everywhere else), and `release.yml` extracts the AppImage (`--appimage-extract`, no FUSE needed) and fails when it carries `package-type`.
- `electron-builder.cjs` sets `publish` only from `GITHUB_REPOSITORY` and to an explicit `null` otherwise: left out, a non-empty `GH_TOKEN` makes electron-builder guess a GitHub feed. The deb's homepage (which its `fpm` target requires) is `package.json`'s `homepage` (set since the repository went public), with the feed's repository as the fallback through `extraMetadata`; with a homepage the Linux targets are the AppImage and the deb, so a local Linux `npm run package` builds both (electron-builder fetches `fpm` itself). `dev-app-update.yml` is gitignored because it names a repository.
- electron-builder treats an empty `WIN_CSC_LINK` as unset, but takes an empty macOS `CSC_LINK` (a secret that is not set) as a certificate, so the config maps a blank one to `identity: null`; in electron-builder 26 `notarize` is a boolean, the credentials coming from `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD` and `APPLE_TEAM_ID`. Read the installed typings, not older docs.
- In `release.yml` the `check` job (read access only) runs `npm ci`, the typecheck and the tests; a separate `draft` job (`contents: write`, no `npm ci`: `scripts/release-check.mjs` needs only Node) creates the draft release once, before the build jobs (three electron-builder jobs uploading in parallel would each create their own), and fails when the tag's release is already published. The build jobs need `draft` on a tag push only (`!cancelled()` with the results checked, since `draft` is skipped by hand). Every checkout has `persist-credentials: false`, and only the packaging step gets `GH_TOKEN`. Check both workflows with actionlint (with shellcheck) after a change.
- Smoke screenshot names are numbered across sections, and `decor-agent-ui.ts` writes `58-snapshot-3d-day.png` and `59-snapshot-3d-night.png` itself: grep `src/main/smoke` for a number before taking it (the update shots are 61 to 63 and 74; the identity's 64 to 73: 64 to 67, 72 and 73 in `identity-ui.ts`, 68 to 71 in `otto-ui.ts`).
- The packaged build runs the smoke too: `release/win-unpacked/<productName>.exe --smoke`.
- Otto's halo stays on the plan for a minute after an assistant-authored edit (or until the next edit by you or an MCP agent, which clears it in 200 ms), drawn under the walls and over rooms and connectors' floors: a smoke pixel probe near something the fake assistant just drew sees mulberry at 22 %. Probe away from it or make a user edit first (`plan.wall.add` through `smoke.run` is a user edit). The canvas mirrors what the last frame drew of Otto's marks (`data-ai-highlights`, `data-ai-tag`, `data-ai-tag-box`, `data-ai-pending`): wait on those, not on a delay. On the duplex ground floor, connectors-ui leaves an elevator at (4000, 6500): a click there selects it, not a wall.
- The fake API reads a held turn's tool input only when `release()` lets it go, so a smoke step can script a turn before the ids it needs exist (the composer's new project's ground floor) and fill `turn.tools[0].input` once they do (`identity-ui.ts`).
- Settings sections registered with `order` ≥ `SETTINGS_LATE` (900) render after the Assistant, just before About; lower ones after Units. A section near the bottom cannot scroll to the top of the tab, so a smoke check that Settings opened scrolled to it accepts the section anywhere in the upper part of the window (as `updates-ui.ts` does), not at the top.
- The bundled fonts live in `src/renderer/src/fonts/` and reach the build only through the `url('./fonts/…')` of the `@font-face` rules in `styles.css`: the Angular builder copies each referenced file into `out/renderer/media/` with a hashed name (there is no `assets` option), which the packaged app loads over `file://` under `font-src 'self'`. A font file nothing references is not shipped; check `out/renderer/media/` after adding one. Canvas text does not wait for a face: the plan view redraws once `document.fonts.load` has the sans and mono, and `view.snapshot`'s plan render waits for them; a new offscreen text render must do the same or it draws in the fallback.
- An empty level shows the "Draw the first wall." guide over the plan canvas (`data-testid=plan-empty`, until the level has an entity or a connector). It is `pointer-events: none` except Otto's line, and that only while the Select tool is on, so a smoke click on an empty level reaches the canvas unless it aims at that line (below the centre). `identity-ui.ts` checks the first-launch guide by moving every project to the trash and restoring them, so it runs last among the UI sections (before `perf.ts`), when no later section needs an open tab.
- The smoke drives a 1440 × 900 window (`createMainWindow`) and every computed click assumes that canvas: a smaller screen clamps the window and moves the clicks off the canvas (the first wall click once landed on the layer opacity slider). `runSmoke` refuses to start in a window smaller than that and says so; CI's Windows runner has a 1024 × 768 screen, so `ci.yml` sets it to 1920 × 1080 before the smoke.
